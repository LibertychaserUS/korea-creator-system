# 11_文案清单与草稿

本文档为 KCS（韩国品牌 × 小红书博主数据系统）的文案规范、术语对照表、禁止外露的技术词与替代说法、三语界面文案清单以及宣传站（Landing Page）完整文案草稿。

本轮文案根据最新产品设计原则进行了全面重构：**文风文科化、技术词不外露，用内容词描述技术本身达到的功能，界面只说“它帮你做到什么”，不说“它是怎么做的”；面向运营和品牌选人同事，彻底消除工程词汇与技术实现细节**。

## 二、术语对照表（Terminology Table）

在所有端（宣传站、运营端、运维端、选人端）与用户沟通中，统一人群术语与核心业务概念：

| 中文规范术语 (zh-CN) | 英文规范术语 (en) | 韩文规范术语 (ko) | 禁用旧词 / 误导表达 | 业务含义与场景 |
|---|---|---|---|---|
| **博主** | Creator | 크리에이터 | 达人 / 网红 / KOL / 账号 | 小红书内容创作者与合作对象，统一称“博主” |
| **数据源** | Data Source | 데이터 소스 | 平台接口 / 抓取库 | 小红书官方数据（蒲公英）与合作数据平台（千瓜、新红） |
| **抓取任务** | Collection Task | 수집 작업 | 拉数任务 / 采集任务 / 爬虫作业 / worker 任务 | 运营人员配置好条件发起的后台收集过程 |
| **统一口径** | Uniform View | 일관된 기준 | 转换层 / 规范化 / 数据清洗 / 算法打分 | 将各平台提供的信息按统一方式整理对照，不猜不补 |
| **指标** | Metric / Metrics | 지표 | 分数 / 维度分 / 权重分 | 平台给出的客观数据或纯算术换算比例，无综合打分 |
| **量级** | Follower Tier | 팔로워 구간 | 梯队 / 级别 / 咖位 | 按粉丝数划分：头部 (≥50万)、腰部 (5-50万)、初级 (5千-5万)、素人 (300-5千) |
| **健康等级** | Health Grade | 건강 등급 | 账号评分 / 风险分 | 小红书官方每月更新：优秀 / 正常 / 异常（低活博主硬门槛） |
| **排位** | Tier Ranking | 구간 내 순위 | 分位 / 排名分 / P75 | 指标在“同一平台 × 同一量级”群体中的相对表现位置 |
| **筛选方案** | Selection Plan | 선정 기준 / 필터 세트 | 评分模型 / 推荐规则 / 权重包 / Query | 保存的选人条件 (≥/≤/区间/排位≥) + 排序 + 高亮提醒 + 显示内容 |
| **项目** | Project | 프로젝트 | 投放案 / 需求包 | 选人团队用于承载候选名单与投放推进的业务单元 |
| **候选名单** | Candidate Shortlist | 후보 명단 | 投放入围表 / 达人池 | 选人端分配进特定项目的博主集合 |
| **演示数据** | Sample Data | 샘플 데이터 | 样例数据 / fixture / 假数据 | 尚未接入真实数据时，展示界面和排版的样例内容 |
| **数据记录** | Data Record | 데이터 기록 | 快照 / snapshot / 存档 | 每次抓取或选入项目时原样保留的历史数据 |
| **归并** | Merge across platforms | 통합 정리 | 身份归并 / 达人合并 | 多个平台记录对应同一小红书号时，自动汇总展示 |

## 三、每个指标（`kcs.metric.*` / `kcs.metricHelp.*`）一句话口径说明

所有指标严格遵循“**平台给什么我们看什么，取不到保持 —，绝不脑补**”原则，使用业务同事听得懂的语言：

| 键名 | 指标名称 (zh-CN) | 一句话口径说明（给运营与品牌选人同事） | 取值来源与缺失处理 |
|---|---|---|---|
| `followers` | 粉丝数 | 平台展示的累计粉丝总数。 | 由小红书或合作平台提供；平台没给时显示 —。 |
| `followerGrowth` | 近期涨粉 | 统计周期内净新增粉丝数。 | 由小红书或合作平台提供；平台没给时显示 —。 |
| `followerGrowthRate` | 涨粉率 | 新增粉丝 ÷ 统计周期开始时的粉丝数。 | 由系统换算；平台没给时显示 —。 |
| `readFanRatio` | 阅读粉丝占比 | 近 30 天读过其笔记的粉丝占粉丝总数的比例（不是阅读里有多少来自粉丝）；高低各有含义，只作参考。 | 由蒲公英提供；平台没给时显示 —。 |
| `activeFanRatio` | 活跃粉丝占比 | 近 30 天内在小红书有打开、浏览等活跃行为的粉丝比例。 | 由蒲公英提供；平台没给时显示 —。 |
| `engagedFanRatio` | 互动粉丝占比 | 近 30 天内与博主笔记有赞藏评等真实互动的粉丝比例。 | 由蒲公英提供；平台没给时显示 —。 |
| `impressionMedian` | 曝光中位数 | 统计周期内日常笔记曝光量的中位数（自然公域流量）。 | 由小红书或合作平台提供；平台没给时显示 —。 |
| `readMedian` | 阅读中位数 | 统计周期内日常笔记真实阅读次数的中位数。 | 由小红书或合作平台提供；平台没给时显示 —。 |
| `interactionMedian` | 互动中位数 | 统计周期内日常笔记（点赞 + 收藏 + 评论）总和的中位数。 | 由小红书或合作平台提供；平台没给时显示 —。 |
| `likeMedian` | 点赞中位数 | 统计周期内日常笔记单篇点赞数的中位数。 | 由小红书或合作平台提供；平台没给时显示 —。 |
| `collectMedian` | 收藏中位数 | 统计周期内日常笔记单篇收藏数的中位数。收藏代表深度种草与购买意向。 | 由小红书或合作平台提供；平台没给时显示 —。 |
| `commentMedian` | 评论中位数 | 统计周期内日常笔记单篇评论数的中位数。 | 由小红书或合作平台提供；平台没给时显示 —。 |
| `coopReadMedian` | 合作阅读中位数 | 经蒲公英报备商业合作笔记的阅读量中位数。 | 由蒲公英提供；平台没给时显示 —。 |
| `coopInteractionMedian` | 合作互动中位数 | 经蒲公英报备商业合作笔记的点赞、收藏与评论中位数。 | 由蒲公英提供；平台没给时显示 —。 |
| `engagementRate` | 互动率 | 互动中位数 ÷ 阅读中位数（按真实阅读计算，不用粉丝数虚标）。 | 由系统换算或蒲公英提供；平台没给时显示 —。 |
| `retentionRate` | 完播率/3S阅读率 | 图文笔记 3 秒阅读率或视频笔记 5 秒完播率。 | 由蒲公英或合作平台提供；平台没给时显示 —。 |
| `noteCount` | 发文数 | 统计周期内在小红书公开发布的笔记总数。 | 由小红书或合作平台提供；平台没给时显示 —。 |
| `viralCount` | 爆文数 | 统计周期内达到千赞或五千赞以上的爆文篇数。 | 由合作数据平台提供；平台没给时显示 —。 |
| `viralRate` | 爆文率 | 爆文数 ÷ 发文数。体现内容表现稳定性。 | 由系统换算；平台没给时显示 —。 |
| `priceImage` | 图文一口价 | 蒲公英报备官方图文合作单篇标准报价（人民币）。 | 由蒲公英提供；平台没给时显示 —。 |
| `priceVideo` | 视频一口价 | 蒲公英报备官方视频合作单篇标准报价（人民币）。 | 由蒲公英提供；平台没给时显示 —。 |
| `cpv` | 单次阅读成本 | 报价 ÷ 合作阅读中位数，单次真实阅读成本。 | 由系统换算；平台没给时显示 —。 |
| `cpe` | 单次互动成本 (CPE) | 报价 ÷ 合作互动中位数，单次真实互动成本（美妆实操通常 ≤ 3 为优选）。 | 由系统换算或蒲公英提供；平台没给时显示 —。 |
| `cpm` | 千次阅读成本 (CPM) | 报价 ÷ 合作阅读中位数 × 1000，千次真实阅读成本。 | 由系统换算；平台没给时显示 —。 |
| `collectLikeRatio` | 收藏点赞比 | 收藏中位数 ÷ 点赞中位数。比值越高说明高价值干货与实用属性越强。 | 由系统换算；平台没给时显示 —。 |
| `purchaseIntentCommentRatio` | 求购评论占比 | 评论中含「求链接、怎么买、多少钱、色号、已下单」等购买意向词的占比。 | 由蒲公英提供；平台没给时显示 —。 |
| `trafficSearchRatio` | 搜索流量占比 | 阅读流量中来自主动搜索的比例；越高代表长尾自然流量与心智沉淀越久。 | 由蒲公英提供；平台没给时显示 —。 |
| `trafficRecommendRatio` | 推荐流量占比 | 阅读流量中来自发现页/信息流推荐的比例；越高代表爆发推流潜力越大。 | 由蒲公英提供；平台没给时显示 —。 |
| `trafficFollowRatio` | 关注流量占比 | 阅读流量中来自博主关注页的比例。 | 由蒲公英提供；平台没给时显示 —。 |
| `readToFollowerRatio` | 读粉比 | 日常阅读中位数 ÷ 粉丝数。高读粉比代表平台正在推荐，内容穿透力强。 | 由系统换算；平台没给时显示 —。 |
| `authenticity` | 粉丝真实度 | 合作机构根据互动行为抽样估算的真实粉丝比例。 | 由合作数据平台提供；平台没给时显示 —。 |
| `coopNoteCount` | 合作笔记数 | 博主在小红书平台累计完成的官方报备商业合作笔记总数。 | 由蒲公英提供；平台没给时显示 —。 |

## 四、宣传页（Landing Page）完整文案草稿

宣传页承载产品定位：**客观、严谨、面向运营与选人团队的博主数据系统**。文风朴素、直接、不卖弄，杜绝“精准预测转化”、“AI全网唯一黑盒”等浮夸承诺。

### 1. Hero 区域
- **眉题 (Eyebrow)**：`听潮 · 品牌出海选人系统`
- **主标题 (H1)**：`小红书博主数据，回归客观指标。`
- **副标题 (Lead)**：`不发明综合分，不搞黑盒加权。直连小红书官方与合作数据平台，按设定条件自动抓取，统一看数口径，在同平台同量级里对比排位，帮品牌团队选出真正有转化力的博主。`
- **主要行动按钮 (CTA Primary)**：`登录工作台 →`
- **次要行动按钮 (CTA Secondary)**：`了解四大工作台`
- **产品底线标签 (Pillars)**：`真实源头 · 客观数据 · 同量级排位 · 数据锁定`

### 2. 产品缩影卡片（Hero 预览）
- **卡片标题**：`博主库`
- **卡片副标**：`已发布 · 按 CPE 升序`
- **表格列**：`博主 | 粉丝量级 | CPE | 粉丝`
- **健康等级门槛**：`健康等级 · 优秀（低活博主硬门槛已排除）`
- **操作动作**：`直接分派到项目候选名单`

### 3. 数据来源与统一口径（Data Sources & Uniform View）
- **区块眉题**：`数据源头`
- **区块标题**：`平台给什么，系统就呈现什么。`
- **区块导语**：`不编造综合分数。派生数据全为公开换算，优劣只在同平台、同量级里对比相对排位，没拿到的数据保持“—”。`
- **官方数据**：
  - 标签：`小红书官方数据（蒲公英）`
  - 说明：`官方通道获取，包含曝光/阅读/互动中位数、图文与视频一口价、CPE、健康等级、粉丝画像及合作品牌。`
- **合作平台**：
  - 标签：`合作数据平台（千瓜、新红）`
  - 说明：`专业数据平台直连，提供行业参考、近期爆文表现、发文频率、粉丝真实度等数据。`
- **统一口径深色卡主张 (`kcs.landing.transformLine`)**：
  - 核心一句话：`不同平台的数据，一套口径看。`
  - 说明文案：`平台给的原始数据都留着，随时可查。口径有调整随时更新，不需要改系统底层。`

### 4. 指标怎么读与同量级排位（Cohorts & Ranking）
- **区块标题**：`指标好与坏，只在同量级、同平台里比。`
- **量级划分 (Tier)**：
  - `头部`：粉丝数 ≥ 50 万
  - `腰部`：粉丝数 5 万 – 50 万
  - `初级`：粉丝数 5 千 – 5 万
  - `素人`：粉丝数 300 – 5 千
- **同量级排位逻辑**：不同量级博主之间 CPE 或互动表现不能直接拉平比。系统将每个指标与同平台、同量级的博主一起排位（前 10%、前 25%、中上、中下、后 25%），清晰看清在同类博主里的真实位置。
- **健康等级一票否决**：小红书官方健康等级每月 1 日更新。「异常（低活博主）」直接硬门槛排除，不参与任何妥协。

### 5. 筛选方案（Selection Plans）
- **区块标题**：`用清晰的选人方案替代主观打分。`
- **区块说明**：`选人公司用自己的语言定义标准。将“量级 = 腰部 + 健康等级 = 优秀 + CPE ≤ 3 + 收藏/点赞 ≥ 0.8”保存为选人方案（如第 1 版、第 2 版）。全团队统一复用，杜绝个人经验流失。`

### 6. 四大工作台介绍（Workspaces）
- **选人端**：`按筛选方案挑博主、建投放项目并整理候选名单。`
- **运营端**：`博主建档入库、数据抓取与分类整理。`
- **运维端**：`查看抓取进度、继续未完成的抓取、检查平台连接与运行状态。`
- **宣传站**：`产品理念、数据口径与多端访问门户。`

## 六、界面结构上仍外露技术词的问题清单（给前端与产品同事）

文案层已在本地化文件中将所有技术工程词替换为业务内容词。但在检查前端组件（`apps/**` 与 `libs/panel/**`）代码实现时，发现若干由于**硬编码（Hardcoded Strings）**或**组件结构绑定**导致技术名词仍然外露的问题，文案修改无法单独生效，需前端同事协助修改代码：

1. **`apps/ops/pages/sources/index.vue` 表单内的参数与技术术语硬编码**：
   - **问题现象**：页面表单部分字段（例如输入框 placeholder 或提示文本）存在前端写死的 `"token"`、`"API Key"` 或 `"PGY_ACCESS_TOKEN"` 提示占位符。
   - **改进建议**：移除任何以技术变量名命名的提示，统一使用 `$t('kcs.source.notConfiguredHint')` 或改为中文提示“请联系管理员在后台完成平台接入”。
2. **`apps/ops/pages/sources/index.vue` 任务模式选择项（Mode Select）**：
   - **问题现象**：下拉选项中写死了 `"fixture"` 模式与 `"live"` 模式的英文字符串。
   - **改进建议**：将下拉展示标签改为绑定 `$t('kcs.source.fixture')`（显示为“演示数据”）和 `$t('kcs.source.live')`（显示为“真实数据”），绝不将底层的模式标识原样渲染在下拉界面中。
3. **`apps/select/pages/index.vue` 筛选方案抽屉中的版本标签**：
   - **问题现象**：部分方案列表或详情头部硬编码拼接了 `"v" + query.version`（如显示 `v1`、`v2`）。
   - **改进建议**：统一使用 `$t('kcs.query.version', { n: query.version })`，在界面上渲染为“第 1 版”、“第 2 版”，符合文科化表述。
