# 抓取流水线与队列

一次抓取 = 一组参数（`SourceQuery`）→ 一个任务（`ingest_jobs`）→ worker 按配额分页调用适配器 → 原始 JSON 落库 → 转换层出指标 → 写快照、归并身份。

```
运营端「数据源」页                API                          worker（API 进程内）
  填参数 ───POST /api/ingest/fetch──▶ 入队 queued ──2s 轮询──▶ 取一个到点任务（全局一条流水线，每来源同时只跑一个）
                                     202 { job }              ├ 令牌桶：ingest_sources.rate_limit 次/分钟
  列表 3s 轮询 ◀── GET /api/ingest/jobs ───────────────────── ├ 日配额：ingest_sources.quota vs ingest_source_usage
                                                              ├ adapter.fetch(query, cursor) → RawRecord[]
                                                              │   creator_raw ← payload 原样
                                                              │   adapter.normalize(raw) → NormalizedCreator
                                                              │   creator_sources 解析/归并 → creators upsert
                                                              │   creator_metrics_history ← 快照
                                                              │   只写 creators.metrics（最新）；发布快照 metrics_locked 永远不碰
                                                              ├ nextCursor 为空或 pages_done = max_pages → ok
                                                              ├ 配额耗尽 → partial，保留 cursor，next_run_at = 次日 00:00
                                                              ├ 适配器抛错 → 暂时性：退避重试至 3 次；永久：立刻停
                                                              └ 停下的整次抓取 / 读不出的单条 → 搁置记录
```

## 参数（SourceQuery）

| 字段 | 说明 | 蒲公英 | 千瓜 / 新红 |
|---|---|---|---|
| `source` | 数据源 | | |
| `window` | 30 / 90 天，决定 `dateType` 与快照 `window` | ✓ | 视合同 |
| `keyword` | 关键词（笔记内容维度） | ✓ | ✓ |
| `followersMin/Max` | 粉丝区间 | ✓ | ✓ |
| `priceMin/Max` | 图文报价区间 | ✓ | 视合同 |
| `category`, `region` | 必须与平台字典完全一致，多一个字返回 0 条 | ✓ | 视合同 |
| `health` | 不含 `abnormal` 时带上"排除低活" | ✓ | — |
| `externalIds[]` | 只刷指定博主；蒲公英会逐个补全 4 个详情接口 | ✓ | ✓ |
| `limit` | 目标条数；换算成 `max_pages` | | |

每个适配器声明 `supports[]`，表单会把不支持的字段置灰。参数到平台请求体的对照见 03。

## 任务状态

| 状态 | 含义 | 界面动作 |
|---|---|---|
| `queued` | 已入队，等 worker | 可取消 |
| `running` | worker 正在翻页 | 可取消 |
| `ok` | 翻完或到 `max_pages` | — |
| `partial` | 日配额用完或被限流；`cursor` 保留，`next_run_at` 后 worker 自动续跑 | 可立刻重试 |
| `failed` | 重试 3 次仍失败，或被取消（`error = cancelled`） | 可重试 |

`pages_done` / `quota_used` 在运营端状态列下方以"第 N 页 · 调用 M 次"显示。

## 速率与配额

- **速率**：每个来源一个内存令牌桶，容量 = `rate_limit`（次/分钟）。付费网关（TikHub / JustOneAPI）按次计费，200 响应即扣费，空结果也扣，所以每页、每次详情补全都计 1。
- **日配额**：`ingest_source_usage(source, day).calls`，`day` 按来源的 `ingest_sources.quota_tz`（默认 `Asia/Shanghai`）算，北京时间 00:00 重置，续跑时间也落在那一刻（UTC 16:00）；到 `quota` 即停，任务转 `partial`。`quota = 0` 等于把这个来源暂停：任务立刻 `partial`，一页都不抓。
- **续跑**：`partial` 的任务到了 `next_run_at`（来源时区的次日 00:00）由 worker 自己从保留的 `cursor` 继续，不需要人点重试；运维端的「重试」只是把这一步提前。
- **并发**：同一来源同时只跑一个任务，避免两个任务互相吃配额。
- `PGY_ENRICH=1` 时搜索结果逐个补全详情（每条 +4 次调用）；默认只存列表字段，按 `externalIds` 刷新时总是补全。

## 抽水：一条流水线，不铺开

付费网关按次计费、按分钟限流，多开 worker 只会把账单和 429 一起翻倍。所以抽水端刻意只有一条流水线：

- 每个 API 进程都带这个循环，但只有抢到 Postgres 顾问锁（`INGEST_QUEUE_LOCK`）的那个真的抽水，其余空转待命 —— 重启或多副本只会换人，不会多一个消费者；
- 每轮只取一个到点的任务，跑完再看下一个；
- 认领时写租约（`locked_by` / `lease_expires_at`，默认 60 秒，每翻一页续一次）。`running` 的任务只有租约过期才允许被接手，因此「进程中途没了」能自动续跑，而不会两边同时抓；同一来源已有活租约时，另一个任务连认领都做不到；
- `INGEST_WORKER=0` 让某个进程完全不参与抽水（只服务 HTTP）。
- 停机（SIGTERM / SIGINT）：不再取新任务；正在跑的任务翻完当前这一页就停，回到 `queued`、保留 `cursor`、清掉租约，然后释放顾问锁——下一个进程接手时立刻从断点续跑，不用等租约过期。等待上限 `SHUTDOWN_TIMEOUT_MS`（默认 25 秒），超时照样退出，任务靠租约过期被接手。
- 日志：每个任务结束 / 失败 / 被挂回写一行 JSON（`ingest.job_done` / `ingest.job_failed` / `ingest.job_partial` / `ingest.job_requeued`），带 `jobId`、`source`、`code`、第几次；错误信息先脱敏，不含凭证。循环本身出错写 `ingest.tick_failed`，不再静默吞掉。

选任务的条件：`queued` 到点、`partial` 到 `next_run_at`、或 `running` 但租约已过期（上一个进程留下的遗留任务）。

## 每日任务

抽水进程（抢到顾问锁的那个）在两个任务之间顺带跑「每日任务」，全集群一天只跑一次：

- 注册：`registerDailyTask(name, fn)`（`apps/api/src/ingest/daily.ts`），`fn(env)` 返回的结果（可 JSON 化）记进 `ingest_daily_runs.result`。本仓库内置的每日任务都在 `apps/api/src/ingest/daily-tasks.ts` 里各占一行注册；容量快照接入时也在那里加一行 `registerDailyTask('capacity', runDailyCapacitySnapshot)`。
- 时间：按 `DAILY_TASKS_TZ`（默认 `Asia/Shanghai`）的自然日，到 `DAILY_TASKS_HOUR`（默认 4 点）之后的第一个抽水轮次开始；`DAILY_TASKS=0` 关掉定时（手动仍可）。
- 一天一次：先在 `ingest_daily_runs(task, day)` 抢到这一行才跑，重启或多副本不会重复；某个任务失败只记 `ok = false` 与原因，不影响其他任务，也不影响抽水。
- 接口：`GET /api/ingest/daily`（各任务最近一次的日期、结果、失败原因，`ingest.read`）；`POST /api/ingest/daily/:task/run` 立刻重跑当天这一次（`ingest.retry`，写审计 `ingest.daily_run`）。
- 任务在抽水循环里串行执行，期间不取新抓取任务；单个任务应在几分钟内结束。

## 价值分层（只打标签，不删）

每日任务 `value-tiers`（`apps/api/src/ingest/tiering.ts`）给每条快照（`creator_metrics_history`）和每次抓取（`creator_raw`）打一个层级，并把依据存进 `tier_features`。**没有任何代码按层级删数据**；将来若要降采样或冷存，先看这个标签。

| 层级 | 条件（按顺序，先中先得） |
|---|---|
| `pinned` 钉住 | 某个决定看到的那份数字：发布、分派、加入候选、下架、导出、详情被查看（结果事件落在它之前最近的一份快照上）、审计里针对该博主的操作；异常的前后两份（同源相邻两份的粉丝 / 阅读中位数 / 互动中位数相对变化 ≥ `TIER_ANOMALY_RATIO`，默认 0.5）；每个来源最新的一份 |
| `change_point` 变化点 | 旋转门算法（swinging door）在任一指标上保留的中间点：从上一个保留点出发，没有一条直线能让之后各点都落在 ±容差之内时，前一个点就是变化点。容差按指标相对计（粉丝 2%、中位数与互动率 10%、报价 5%、CPE 10% 等），`TIER_TOLERANCES`（JSON，如 `{"followers":0.05}`，`null` 去掉某项）可改 |
| `downsample` 可降采样 | 其余，且不超过 `TIER_COLD_AFTER_DAYS`（默认 180）天 |
| `cold` 可冷存 | 其余，且更旧 |

- 按来源分开算：蒲公英与千瓜各是一条线，两家口径差不会被当成异常。
- 原始抓取跟随同一时刻的快照；没有对应快照的（同日重复抓取）按年龄记 `downsample` / `cold`。
- 结果事件：读线 A 的 `creator_outcome_events(creator_id, kind, occurred_at)`（`kind` ∈ publish / assign / remove / export / view）；该表建好前，用已有记录代替（发布时间、审核通过、分派、候选、下架审计），导出与查看暂无来源（`apps/api/src/ingest/outcome-events.ts`）。
- 每次全部重算（新的发布或分派可能让旧快照变成钉住），结果计数记在 `ingest_daily_runs.result`。

## 失败：先分清值不值得重试

| 情况 | 判断 | 动作 |
|---|---|---|
| 平台 5xx / 429 / 超时 | 暂时性 | 2 秒、4 秒退避，最多 `max_attempts`（默认 3）次 |
| 平台 4xx（401 / 403 / 404 / 422） | 永久 | 第一次就停，不空转 |
| 接入信息不全、未知来源、返回结构里没有记录列表 | 永久 | 第一次就停，不空转 |

判断在 `classifyIngestFailure()`，错误信息写库前过一遍脱敏（`token=***`），凭证不会进数据库也不会上界面。

## 搁置记录（死信队列）

没能完成的东西一律留档，不静默丢弃。两类，且只有这两类：

| 类型 | 什么时候产生 | 留下什么 | 重放做什么 |
|---|---|---|---|
| `job`（整次抓取） | 重试用尽，或永久失败 | `query` + `cursor` + 次数 | 按原参数从游标**续跑**，新建一个任务并回填 `replay_job_id` |
| `record`（单个博主） | 某条读不出来（`RECORD_INVALID`）或写不进去（`RECORD_WRITE_FAILED`） | 平台原始 JSON | 用留下的 JSON 重读入库，**不打平台、不计配额** |

- 队列自己永远不会重放搁置记录：能成功的前提是有人改了东西（凭证、字段对应关系、平台那边恢复），自动空转只会烧钱。
- 同一条博主反复失败只更新那一条（`(source, external_id)` 上的部分唯一索引），不堆重复；`attempts` 记累计次数。
- 重放失败会把 `replay_count` 加一并留在待处理里；到 `DEAD_LETTER_MAX_REPLAYS`（3）次界面不再提供「再试一次」，先去改设置。
- 运维端直接点任务「重试」时，这个任务的搁置记录会一起结掉（`state = replayed`，指向同一任务），不留孤儿。
- 表：`ingest_dead_letters(kind, state, source, job_id, external_id, code, message, attempts, replay_count, query, cursor, payload, replay_job_id, resolved_at, resolved_by)`。
- 接口：`GET /api/dev/dead-letters?state=&kind=&source=`、`GET /api/dev/dead-letters/:id`、`POST .../replay`、`POST .../dismiss`（看需要 `dev.read`，处理需要 `dev.retry`）。`GET /api/dev/health` 带 `deadLetters` 计数与当前在抓的来源。
- 界面上叫「搁置记录」，不说「死信」：一张表列出类型、人话原因、试过几次，右侧「再试一次 / 不再处理」。

## 保留期限：现阶段全部保留

**现阶段所有数据都保留，默认不删任何东西**（用户决定）。清理代码仍在，但每一类都要运维显式设成正数才会执行；不设 = 这一类全留。

打开任一类后，抽水进程（抢到 `INGEST_QUEUE_LOCK` 的那个）按 `RETENTION_INTERVAL_HOURS`（默认 24）清一次，抢到锁后先清一次；锁只有一把，所以全集群同一时刻只有一个进程在删。每类分批删（每批 5000 行），第一次清很久没清过的库也不会长时间锁表。

| 数据 | 默认 | 打开方式（正数才生效；`0` 或不设 = 全留） |
|---|---|---|
| `creator_raw` 平台原始 JSON（每次抓取一行；内容相同的原文在 `raw_payloads` 只存一份，属无损去重） | 全留 | `RETENTION_RAW_PER_SOURCE=N`：每个（博主，来源）只留最新 N 条，随后删掉没人再指向的 `raw_payloads` |
| `ingest_dead_letters` 已处理（`replayed` / `dismissed`） | 全留；待处理的无论如何都不删 | `RETENTION_DEAD_LETTER_DAYS=N`：结掉后 N 天（按 `resolved_at`） |
| `audit_logs` | 全留 | `RETENTION_AUDIT_DAYS=N` |
| `creator_metrics_history` 历史快照 | 永久，不参与清理（趋势线靠它，平台补不回来） | — |

`RETENTION_INTERVAL_HOURS=0` 关闭整个检查。每次清完写一行 JSON 日志 `retention.sweep`，带各类删了多少；失败写 `retention.failed`，不影响抽水。实现在 `apps/api/src/ingest/retention.ts`。

## 同步模式

`POST /api/ingest/fetch?sync=1` 不入队，当场跑完返回 201 与结果（`writtenCount` / `skippedDupes` / `failedCount` / `sourceMode`）。用于测试和 fixture 演示；生产界面走 202 入队。

## fixture 模式

来源缺少凭证（`PGY_ACCESS_TOKEN` / `QIANGUA_TOKEN` / `XINHONG_TOKEN`）时适配器返回 `apps/api/src/adapters/fixtures/<source>.json`，字段形状与真实响应一致；任务 `source_mode = fixture`，界面上每个来源徽标都带"样例"标记。fixture 不计配额：worker 发现这一页是样例数据会把预留的那次调用退回去，`quota_used` 保持 0。

## 转换层约束

- 取不到的数字保持 `null`，界面显示"—"。不用默认值、不推测。
- 数字写法统一走契约 `parseNumber()`：`万/萬/w`、`亿/億`、`千/k`、`M/百万`、韩文 `천/만/억`、千分位逗号、全角数字、负号（含 `−` U+2212、全角 `－`）、科学计数法；单位按十进制换算（`0.07万` 恰好是 700，不会出现 700.0000000000001）。`10万+` 取下限并记 `lowerBound`；`5000-8000` 这类区间、`—` / `-` / `暂无` 等占位一律 `null` 并记 `range` / `placeholder`；认不出记 `unparseable`。计数字段取整，负数（涨粉除外）或超过 integer 上限（2147483647）记 `outOfRange` 不写入；金额与单价不得为负。警告以 `<字段>.<原因>` 进 `warnings[]`。
- 供应商响应与演示数据先取原文再解析：超过 2^53 的整数（如长 ID）保留原文数字串，不会被四舍五入成同一个 ID。
- 取值时占位符算缺失：`{粉丝数: "-", fans_count: 5000}` 取到 5000，不会被 `-` 挡住。
- 中位数 / 报价 / 单价（`ZERO_MEANS_HIDDEN_KEYS`）为 `0` 表示"未展示"：三个来源和表格导入一律按 `null` 处理并记 `<字段>.notShown`，不会以 CPE=0 排进前 10%；某个别名是 0 时继续看下一个别名。笔记数、涨粉的 0 是真实的 0，照写。
- 比率的单位逐字段声明，不按数值大小猜：`percent` 字段 `"91"` / `0.8` 分别是 91% / 0.8%，`ratio` 字段 `0.91` 是 91%、`1.2` 就是 120%；带 `%` / `％` 的字串一律按百分数。千瓜 `粉丝真实度`/`爆文率`、新红 `粉丝真实度`/`互动粉丝比`、蒲公英各 `*Rate` 为 `percent`，蒲公英 `pagePercentVo` 为 `ratio`。`<来源>_FIELD_MAP` 可写 `{"paths": [...], "unit": "percent"}` 改单位，只给路径则沿用默认单位。占比类字段（读者粉丝比、活跃粉丝比、互动粉丝比、完播率、爆文率、种草评论比、流量来源、粉丝真实度）超出 0–1 记 `outOfRange` 不写入。
- 健康等级只有两级（蒲公英 2024-09 起「健康 / 异常」，每月 1 日评定）：`toHealthLevel()` 把「健康 / 正常 / 优秀 / 良好 / 普通」都认作健康、「异常」认作异常，`metrics.health` 只会是 `normal` / `abnormal` / `null`，不再产出 `excellent`（迁移 `0043` 把存量里的 `excellent` 改标为 `normal`，发布快照不动）。低活跃是另一件事：蒲公英 `lowActive` 写进 `signals.lowActive`，不再推成健康等级；蒲公英接口里没有确认过的健康等级字段，所以蒲公英博主的 `health` 暂为 `null`（待实测）。按健康筛选时，「异常」与「低活跃」一起算作要排除的一类（与蒲公英 `excludeLowActive` 一致）。
- 共享指标装不下、或不能混在一起的来源事实放在 `signals`（契约 `SourceSignals`，键名与线 A 契约的指标同名：`completionRate`、`read3sRate`、`fanInteractionRatio`、`storeVisitUnitPrice`、`platformRanks`、`lowActive`，合并后可直接搬进指标；存 `creators.source_signals` 与每条快照的 `creator_metrics_history.signals`）：健康等级、低活跃、近 7 天是否活跃、视频完播率与图文 3 秒阅读率（分开两个字段；`retentionRate` 暂仍是完播率）、合作笔记总数（`coopNoteCount` 只取近 30 天 `coopNoteNum30d`，不再拿累计的 `businessNoteCount` 兜底）、新红「互动粉丝比」（口径未公开，不再写进蒲公英的 `engagedFanRatio`）、蒲公英「超过 X% 同类博主」各项（`platformRanks`，0–1）、外溢进店 UV 中位数与外溢进店单价（字段名 `mCpuvNum` / `estimateCpuv*` 待实测），以及各字段实际覆盖的天数（`windowDays`：活跃粉丝占比 28 天，互动 / 阅读粉丝占比与合作笔记 30 天）。
- 派生比率（`readToFollowerRatio`、`collectLikeRatio`、`engagementRate` 缺失时用 中位数相除）在 `deriveMetrics()` 统一算，适配器不算。
- 转换层每个字段带 `warnings[]`（缺失 / 供应商估算），存在 `NormalizedCreator`，运营端原始数据抽屉可见。

## 入库：只有一处

博主进库只有一个函数：`upsertCreatorFromNormalized()`（`apps/api/src/ingest/persist.ts`）。队列翻到的一页、搁置记录的重放、运营上传的表格，三条路都调它，所以行为一致：

| 做什么 | 规则 |
|---|---|
| 找人 | 有小红书号时先按号找：号的主人优先（这条记录的来源链接移过去，原先那位的原始 JSON 与快照不动）；否则依次 `creator_sources(source, external_id)` → `creator_key`；都没有才新建 `draft`。两个写入同时新建同一个号时，后到的重试一次并落到先到的那位上 |
| 写什么 | 最新数字（`metrics`、`followers` …）+ `needs_review = true`。`status`、`metrics_locked`、`metrics_locked_at`（发布快照）**永远不碰**，只有发布会动 |
| 空值 | 这次没带的粉丝数 / 地区 / 领域 / 小红书号保留原值，不被抹掉 |
| 附带记录（仅来自数据源的） | `creator_sources` 链接、`creator_raw` 原样 JSON、一条 `creator_metrics_history` |
| 表格行 | 只带粉丝与图文报价，只改这两项（其余平台指标保留）；不写历史快照（人填的数不是平台测量），原文件留在对象存储 `batches/<任务 id>/`。新建的博主带「没合作过的」、报价与一条待校对审核。数字与数据源同一个解析器（`1.2万`、`1.2E+7` 都认）；`暂无` / `-` 记为未知；区间（`5000-8000`）、负数、认不出的写法整行进搁置记录，不写成错数。同名不同人不合并：没有 `userId` / 小红书号的行各自新建，不拿昵称当身份。表格按真正的 XML 读：`<c .../>` 这类带样式的空单元格、省略 `r` 的单元格都不会让后面的列错位 |
| 失败 | 每个博主一个事务，中途失败什么都不留；来自数据源的那条与表格行都进搁置记录（`RECORD_INVALID` / `RECORD_WRITE_FAILED`），表格行另计入 `failedCount`。表格行的搁置记录 `source = file-drop`、`externalId = <任务 id>#<行号>`，`payload` 是那一行的单元格（带文件名），重放时按同样规则重读，不需要原文件 |

开任务只有两个入口：`POST /api/ingest/fetch`（数据源，走队列、扣配额、限速）与 `POST /api/ops/batches`（表格，必须带文件）。旧的 `POST /api/ingest/jobs` 已下线（410）：它绕过队列当场跑，数据源不是适配器时还会凭空造一个「投递达人」。

## 身份归并

蒲公英给 `redId`（小红书号），千瓜 / 新红导出通常也带小红书号。归并只认小红书号，不认昵称（同一来源的同一 id 先按 `creator_sources` 认，见上表）。供应商 id 只在本供应商内唯一：`creator_key` = `<来源>:<id>`（如 `qiangua:10001`），没有小红书号的记录 `xhs_id` 留空、不拿供应商 id 充数，所以千瓜 10001 与新红 10001 是两个人。小红书号只有一种写法：去首尾空白（含全角空格）、全角转半角、小写（`"Cheongdam_Skin "` 与 `"cheongdam_skin"` 是同一个号），契约 `normalizeXhsId()` 与数据库触发器 `kcs_normalize_xhs_id` 规则相同，一个号只属于一个博主（唯一索引）。迁移 `0042` 把存量里只差写法的博主合并：已上架的（其次有发布快照的、再其次最早的）留下，其余所有关联行移过去，被并掉的行与移不过去的重复关联原样留在 `creator_merges`。迁移 `0040` 把旧规则误合并的博主按各链接原始 JSON 里的小红书号拆开（最早那条链接留在原博主上，其余拆成新的草稿并带走自己的原始 JSON、快照与链接）。归并后：

- `creators` 一条；`creator_sources` 每个来源一条链接；
- `creator_metrics_history` 里两源的快照并存，`source` 不同；
- 分位仍按 `source × tier` 分组计算，不跨源比较；
- 选人端详情页"数据来源"卡列出所有链接与最后抓取时间。
