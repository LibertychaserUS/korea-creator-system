# 抓取流水线与队列

一次抓取 = 一组参数（`SourceQuery`）→ 一个任务（`ingest_jobs`）→ worker 按配额分页调用适配器 → 原始 JSON 落库 → 转换层出指标 → 写快照、归并身份。

```
运营端「数据源」页                API                          worker（API 进程内）
  填参数 ───POST /api/ingest/fetch──▶ 入队 queued ──2s 轮询──▶ 取一个到点任务（全局一条流水线，每来源同时只跑一个）
                                     202 { job }              ├ 令牌桶：ingest_sources.rate_limit 次/分钟
  列表 3s 轮询 ◀── GET /api/ingest/jobs ───────────────────── ├ 日配额：ingest_sources.quota vs ingest_source_usage
                                                              ├ adapter.fetch(query, cursor) → RawRecord[]
                                                              │   creator_raw ← payload 原样
                                                              │   adapter.normalize(raw) → NormalizedCreator
                                                              │   creator_sources 解析/归并 → creators upsert
                                                              │   creator_metrics_history ← 快照（每人每源每天一份，当天再抓覆盖）
                                                              │   只写 creators.metrics（最新）；发布快照 metrics_locked 永远不碰
                                                              ├ nextCursor 为空或 pages_done = max_pages → ok
                                                              ├ 配额耗尽 → partial，保留 cursor，next_run_at = 次日 00:00
                                                              ├ 适配器抛错 → 暂时性：退避重试至 3 次；永久：立刻停
                                                              └ 停下的整次抓取 / 读不出的单条 → 搁置记录
```

## 参数（SourceQuery）

| 字段 | 说明 | 蒲公英 | 千瓜 / 新红 |
|---|---|---|---|
| `source` | 数据源 | | |
| `window` | 30 / 90 天，决定 `dateType` 与快照 `window` | ✓ | 视合同 |
| `keyword` | 关键词（笔记内容维度） | ✓ | ✓ |
| `followersMin/Max` | 粉丝区间 | ✓ | ✓ |
| `priceMin/Max` | 图文报价区间 | ✓ | 视合同 |
| `category`, `region` | 必须与平台字典完全一致，多一个字返回 0 条 | ✓ | 视合同 |
| `health` | 不含 `abnormal` 时带上"排除低活" | ✓ | — |
| `externalIds[]` | 只刷指定博主；蒲公英会逐个补全 4 个详情接口 | ✓ | ✓ |
| `limit` | 目标条数；换算成 `max_pages` | | |

每个适配器声明 `supports[]`，表单会把不支持的字段置灰。参数到平台请求体的对照见 03。

## 任务状态

| 状态 | 含义 | 界面动作 |
|---|---|---|
| `queued` | 已入队，等 worker | 可取消 |
| `running` | worker 正在翻页 | 可取消 |
| `ok` | 翻完或到 `max_pages` | — |
| `partial` | 日配额用完或被限流；`cursor` 保留，`next_run_at` 后 worker 自动续跑 | 可立刻重试 |
| `failed` | 重试 3 次仍失败，或被取消（`error = cancelled`） | 可重试 |

`pages_done` / `quota_used` 在运营端状态列下方以"第 N 页 · 调用 M 次"显示。

## 速率与配额

- **按次计费，逐次预留**：真正发出的每一次付费请求（列表、详情、每一项补全）都走适配器层的「计费调用」（`apps/api/src/adapters/billing.ts` 的 `billedCall`，队列那头是 `apps/api/src/ingest/meter.ts`）：发请求**之前**先取 1 个令牌、在当天的用量行上用一条带条件的 UPDATE 预留 1 次调用和它的单价（`calls < quota` 且 `cost + 单价 ≤ 预算` 才成功），拿不到就一次也不发；**之后**按供应商的计费规则结算：
  - TikHub：只有 HTTP 200 计费，200 且 `data` 为空也计费（记一次「查无结果」）；400 / 401 / 402 / 429 / 5xx 都不计费，预留的次数和金额退回；
  - 发出后超时：拿不准是否扣费，按已扣费留着，另记 `maybe_billed`；连接被拒 / 域名解析失败：请求没出门，退回；
  - 千瓜 / 新红 / JustOneAPI / 官方开放平台：没有公开的计费规则，凡是有回话都按计费算（保守）。
  所以一页扇出 81 次调用就是 81 次预留，额度和预算都卡在「刚好到」的那一次，不会像以前那样一页里先花出去再补记、超出一截。适配器声明 `metered: true` 才走这条路；没声明的适配器（测试替身）仍按「每页预留 1 次、取完补记 `SourcePage.calls`」。
- **速率**：每个来源一个令牌桶，容量 = `rate_limit`（次/分钟），连续回填，**每次调用取 1 个**（以前是每页 1 个）；桶的状态存在 Postgres（`ingest_rate_buckets`，迁移 0048），取令牌是一条带条件的 upsert，重启或换进程接手时接着用剩下的令牌，而不是又得到一整桶。改了 `rate_limit` 从新容量的满桶开始。
- **日配额（次数）**：`ingest_source_usage(source, day).calls` = 当天**计费**的调用数，`day` 按来源的 `ingest_sources.quota_tz`（默认 `Asia/Shanghai`）算，北京时间 00:00 重置，续跑时间也落在那一刻（UTC 16:00）；到 `quota` 即停，任务转 `partial`（`QUOTA_EXHAUSTED`）。`quota = 0` 等于把这个来源暂停：任务立刻 `partial`，一次都不发。同一行还记 `requests`（发出的请求，含不计费的）、`unbilled`、`maybe_billed`、`empty_results`、`unpriced_calls`。
- **日预算（金额）**：`ingest_sources.daily_budget_usd`（迁移 0080；蒲公英默认 **$5**，千瓜 / 新红默认不设）对当天 `cost_micros` 设上限，环境变量 `PGY_DAILY_BUDGET_USD` / `QIANGUA_DAILY_BUDGET_USD` / `XINHONG_DAILY_BUDGET_USD` 优先（填 `none` = 不设上限）。到了上限任务转 `partial`（`BUDGET_EXHAUSTED`），和次数额度一样在来源时区的次日 00:00 自己续跑。单价表是 `@kcs/contract` 的 `VENDOR_PRICES_USD`（按 `<网关>:<路径前缀>` 最长匹配：TikHub 蒲公英 $0.02/次、笔记评论 $0.01、笔记组件 $0、App/Web 小红书 $0.01、账户接口免费），`KCS_VENDOR_PRICES`（JSON）可覆盖或补上没有公开价的网关；没有单价的调用只计次数，不计金额（运维端会标出来）。
- **中途停下不丢已付费的数据**：一页做到一半被额度 / 预算 / 停机拦下，已经拿到的博主照常入库，`cursor` 指向第一个没拿到的（`@3` = 刷新列表里的第 4 个 id；`5:7` = 第 5 页跳过前 7 个），`pages_done` 不加一；下次从那里接着做。
- **续跑**：`partial` 的任务到了 `next_run_at`（来源时区的次日 00:00）由 worker 自己从保留的 `cursor` 继续，不需要人点重试；运维端的「重试」只是把这一步提前。
- **并发**：同一来源同时只跑一个任务，避免两个任务互相吃配额。
- **任务上的账**：`ingest_jobs.quota_used`（计费次数）、`cost_micros`、`vendor_requests`、`empty_count` 逐次更新，任务中途失败也是准的；`vendor_notes` 留最近 50 条「查无结果 / 单条被拒」。每次调用写一行 `vendor.call` 日志（端点、状态码、`requestId`、是否计费、耗时）。
- 运维端「调用与额度」：每个来源今天的计费次数 / 次数上限、花费 / 金额上限、发出多少次其中多少次没收费、查无结果、超时可能已扣费、没有单价的调用，以及最近 7 天每天的次数和金额。
- **读回话（蒲公英）**：TikHub 的回话有两层——外层 `{code: 200, request_id, data}`，`data` 里是蒲公英原样的 `{code, success, msg, data}`。外层 `code` 不是 200，或内层 `success: false` / `code` 不是 0，就算「平台说这次失败了」（`VENDOR_INNER_ERROR`）：照样计费，重试也一样，不重试，整次抓取进搁置记录；刷新里某一个博主的详情被这样拒了，只跳过这一个并记在任务上。`data` 为空 = 查无结果：计费、计数（`empty_results` / `empty_count`）、在任务的 `vendor_notes` 里留一条（端点、博主、`requestId`），刷新时照旧记「这次没找到」。单次调用超时 `PGY_TIMEOUT_MS`，默认 60 秒（TikHub 转发给平台，慢；超时的调用可能已扣费，所以宁可多等不急着重发）。
- **补全不再吞错**：四项数据（数据概览、粉丝概览、笔记表现、粉丝画像）逐项调用。某项查无结果 → 这项留空，payload 记 `kcsEmpty`，博主带 `<项>.empty` 提示；某项被平台在 200 里拒了 → 这项留空，payload 记 `kcsIssues`，博主带 `<项>.fetchFailed` 提示；超时 / 429 / 5xx / 额度或预算拦下 → 这一页停在这个博主，已拿到的入库，下次从这个博主整个重来，不会把缺了一块的数据当成完整的存下去。
- `PGY_ENRICH=1` 时搜索结果逐个补全详情（每条 +4 次调用）；默认只存列表字段，按 `externalIds` 刷新时总是补全（每人 = 详情 1 + 数据 4 = 5 次）。

## 抽水：一条流水线，不铺开

付费网关按次计费、按分钟限流，多开 worker 只会把账单和 429 一起翻倍。所以抽水端刻意只有一条流水线：

- 每个 API 进程都带这个循环，但只有抢到 Postgres 顾问锁（`INGEST_QUEUE_LOCK`）的那个真的抽水，其余空转待命 —— 重启或多副本只会换人，不会多一个消费者；
- 每轮只取一个到点的任务，跑完再看下一个；
- 认领时写租约（`locked_by` / `lease_expires_at`，默认 60 秒，每翻一页续一次）。`running` 的任务只有租约过期才允许被接手，因此「进程中途没了」能自动续跑，而不会两边同时抓；同一来源已有活租约时，另一个任务连认领都做不到；
- `INGEST_WORKER=0` 让某个进程完全不参与抽水（只服务 HTTP）。
- 停机（SIGTERM / SIGINT）：不再取新任务；正在跑的任务翻完当前这一页就停，回到 `queued`、保留 `cursor`、清掉租约，然后释放顾问锁——下一个进程接手时立刻从断点续跑，不用等租约过期。等待上限 `SHUTDOWN_TIMEOUT_MS`（默认 25 秒），超时照样退出，任务靠租约过期被接手。
- 日志：每个任务结束 / 失败 / 被挂回写一行 JSON（`ingest.job_done` / `ingest.job_failed` / `ingest.job_partial` / `ingest.job_requeued`），带 `jobId`、`source`、`code`、第几次；错误信息先脱敏，不含凭证。循环本身出错写 `ingest.tick_failed`，不再静默吞掉。

选任务的条件：`queued` 到点、`partial` 到 `next_run_at`、或 `running` 但租约已过期（上一个进程留下的遗留任务）。

## 每日任务

抽水进程（抢到顾问锁的那个）在两个任务之间顺带跑「每日任务」，全集群一天只跑一次：

- 注册：`registerDailyTask(name, fn)`（`apps/api/src/ingest/daily.ts`），`fn(env)` 返回的结果（可 JSON 化）记进 `ingest_daily_runs.result`。本仓库内置的每日任务都在 `apps/api/src/ingest/daily-tasks.ts` 里各占一行注册；容量快照接入时也在那里加一行 `registerDailyTask('capacity', runDailyCapacitySnapshot)`。
- 时间：按 `DAILY_TASKS_TZ`（默认 `Asia/Shanghai`）的自然日，到 `DAILY_TASKS_HOUR`（默认 4 点）之后的第一个抽水轮次开始；`DAILY_TASKS=0` 关掉定时（手动仍可）。
- 一天一次：先在 `ingest_daily_runs(task, day)` 抢到这一行才跑，重启或多副本不会重复；某个任务失败只记 `ok = false` 与原因，不影响其他任务，也不影响抽水。
- 接口：`GET /api/ingest/daily`（各任务最近一次的日期、结果、失败原因，`ingest.read`）；`POST /api/ingest/daily/:task/run` 立刻重跑当天这一次（`ingest.retry`，写审计 `ingest.daily_run`）。
- 任务在抽水循环里串行执行，期间不取新抓取任务；单个任务应在几分钟内结束。

### TikHub 余额（`vendor-balance`）

蒲公英走 TikHub 且配了 key 时，每日任务 `vendor-balance`（`apps/api/src/ingest/balance.ts`）调一次 TikHub 自己的账户接口 `GET /api/v1/tikhub/user/get_user_info`（**免费**，不占次数额度与金额预算），读 `data.user_data.balance` 与 `free_credit`（字段名按 TikHub 文档，**待实测**），每次结果（含失败原因与 `request_id`）存一行 `vendor_balance_checks`，不删。

- 可用余额 = 余额 + 赠送额度；低于 `TIKHUB_BALANCE_ALERT_USD`（默认 5 美元）时写审计 `vendor.balance_low`（操作人为空 = 系统），运维端首页出黄色提醒卡。
- 约可用天数 = 可用余额 ÷ 近 7 天里**有调用的日子**的日均花费（`ingest_source_usage.cost_micros`）；安静的一周会偏保守。最近 7 天没花钱就不给天数。
- 运维端「调用与额度」页顶部显示余额、赠送额度、提醒线、日均花费、约可用天数、上次查询时间与失败原因；有 `dev.retry` 的人可点「立即查询」（`POST /api/dev/vendor-balance/check`，审计 `vendor.balance_checked`）。查询失败时仍显示上一次成功的余额并注明失败。
- 蒲公英不走 TikHub（JustOneAPI / 官方）或没配 key 时这项不跑、不显示，也不发任何请求。

## 价值分层（只打标签，不删）

每日任务 `value-tiers`（`apps/api/src/ingest/tiering.ts`）给每条快照（`creator_metrics_history`）和每次抓取（`creator_raw`）打一个层级，并把依据存进 `tier_features`。**没有任何代码按层级删数据**；将来若要降采样或冷存，先看这个标签。

| 层级 | 条件（按顺序，先中先得） |
|---|---|
| `pinned` 钉住 | 某个决定看到的那份数字：发布、分派、加入候选、下架、导出、详情被查看（结果事件落在它之前最近的一份快照上）、审计里针对该博主的操作；异常的前后两份（同源相邻两份的粉丝 / 阅读中位数 / 互动中位数相对变化 ≥ `TIER_ANOMALY_RATIO`，默认 0.5）；每个来源最新的一份 |
| `change_point` 变化点 | 旋转门算法（swinging door）在任一指标上保留的中间点：从上一个保留点出发，没有一条直线能让之后各点都落在 ±容差之内时，前一个点就是变化点。容差按指标相对计（粉丝 2%、中位数与互动率 10%、报价 5%、CPE 10% 等），`TIER_TOLERANCES`（JSON，如 `{"followers":0.05}`，`null` 去掉某项）可改 |
| `downsample` 可降采样 | 其余，且不超过 `TIER_COLD_AFTER_DAYS`（默认 180）天 |
| `cold` 可冷存 | 其余，且更旧 |

- 按来源分开算：蒲公英与千瓜各是一条线，两家口径差不会被当成异常。
- 原始抓取跟随同一时刻的快照；没有对应快照的（同日重复抓取）按年龄记 `downsample` / `cold`。
- 结果事件：读 `creator_events`（`0025`，只追加）并换成本处的分类：`publish` → 发布、`unpublish` / `unassign` → 移出、`assign` → 分派、`export` → 导出、`detail_view` → 查看；另外两类它不记，从各自的表读：加入候选名单（`shortlist_items`）、`creator_events` 建表前的发布（`creators.metrics_locked_at` 且没有发布事件）。见 `apps/api/src/ingest/outcome-events.ts`。
- 每次全部重算（新的发布或分派可能让旧快照变成钉住），结果计数记在 `ingest_daily_runs.result`。

## 调度器：刷新老博主 + 发现新博主

每日任务 `scheduler`（`apps/api/src/ingest/scheduler.ts`）为每个来源排当天的抓取。**默认只算不排**：计划照样算好存进 `ingest_scheduler_state`、运维端可看；设 `INGEST_SCHEDULER=1` 才真的入队（会花供应商的钱）。

- **预算**：来源日配额 × `SCHEDULER_BUDGET_SHARE`（默认 0.8，其余留给人手动抓）− 今天已用。上一轮排的任务还没跑完时这个来源本轮跳过。
- **刷新**：按外部 ID 取详情（`externalIds`，每个任务 20 个）。谁先：到期（`creator_sources.next_refresh_at`）的里面，在用的（已发布、已分派、在候选里）优先，再按到期早晚。蒲公英每刷新一人按 5 次调用估算（详情 + 4 个数据接口），千瓜 / 新红按 1 次。
- **单人刷新间隔（泊松变化模型）**：每次写入都拿这份快照和同一来源更早一天的最后一份比（同一天再抓一次是替换当天那次比较，不算多一次），数字有没有实质变化（超过容差）。累计比较次数 n、变化次数 X、平均间隔 Ī，用 Cho & Garcia-Molina 估计 λ = −ln((n − X + 0.5)/(n + 0.5)) / Ī（每天变化次数），下次在「变化概率达到 50%」时到期：t = ln 2 / λ，限制在 1–30 天；比较不足 3 次先按 7 天。参数 `REFRESH_TARGET_PROBABILITY` / `REFRESH_MIN_DAYS` / `REFRESH_MAX_DAYS` / `REFRESH_DEFAULT_DAYS` / `REFRESH_MIN_VISITS`。
- **发现**：到点的保存条件（`ingest_discovery_searches`，每条可设最多几页、每隔几小时），按上次入队时间先后。
- **额度分配（Thompson 采样）**：两个「臂」各自的收益率用 Beta(1 + 成功, 1 + 失败) 表示——刷新的成功 = 近 30 天刷新任务写入的快照里「数字实质变化且博主在用」；发现的成功 = 近 60 天发现任务第一次带进来的博主后来被发布 / 分派 / 加入候选。刷新份额 = P(刷新收益 ≥ 发现收益)（蒙特卡洛 4000 次，即批量版 Thompson 采样），夹在 [`SCHEDULER_REFRESH_MIN` 0.5, 1 − `SCHEDULER_DISCOVERY_MIN` 0.1] 之间；两臂各不足 `SCHEDULER_MIN_TRIALS`（30）次时用起始 70 / 30（`SCHEDULER_START_REFRESH_SHARE`）。一方用不完的额度（没有到期的人 / 没有到点的条件）让给另一方。
- **结果事件**：发现的收益读线 A 的结果事件表（见 §价值分层）；表建好前用已有记录代替。
- 运维端：`GET /api/ingest/scheduler` 给出上次计划、两臂的数字、份额是怎么来的（`split.method` = `start` / `thompson`、`winProbability`）、当前参数与各来源到期人数；发现条件在 `/api/ingest/discovery-searches` 增改。排出的任务 `schedule` 为 `refresh` / `discovery`，`opened_by = scheduler`，与手动任务（`once`）走同一条队列、同样受配额与限速约束。

## 数据状态：较久未更新、平台上已找不到、有新数字可重新发布

`apps/api/src/ingest/data-status.ts`。只做数据侧判断，**不改 `status`、不删任何东西**；界面由运营端呈现。博主池把带 `platform_missing_at` 的博主当作不在池里：窄表 `creator_published` 里没有它的行（标记与清除时同一事务重排所在组），选人端详情、走势、加入候选、分派都按 404 / 不在池中处理。

- **数据较久未更新**：`metrics_fetched_at` 早于 `DATA_STALE_DAYS`（默认 30）天前。
- **平台上已找不到**：只看按外部 ID 刷新的任务（`externalIds`），而且要翻完最后一页、不是演示数据，才能说「这个 id 没回来」；每页取到的 id 累计进 `ingest_jobs.seen_external_ids`。要了没回来的 id 在 `creator_sources.miss_count` 上加一，连续 `PLATFORM_MISSING_AFTER`（默认 3）次就在链接上记 `missing_at`、在博主上记 `platform_missing_at`，写审计 `creator.platform_missing`（系统操作）。之后任何一次抓到这个 id（刷新、搜索、死信重放都算）自动归零并清掉标记。运营确认：`POST /api/ingest/data-status/:creatorId/missing`，`keep` 清掉标记（回到池子），`gone` 记确认时间（继续留在池外），都写审计。搜索没搜到不算：列表里没有不等于平台上没有。
- **有新数字，可重新发布**：已发布过的博主，最新数字与发布快照 `metrics_locked` 相比有指标超过容差（与刷新模型的「实质变化」同一套容差），且最新抓取晚于发布时间。每次写入时算一次存进 `creators.republish_changes`，每日任务 `data-status` 全部重算；刚重新发布过的（算的时间早于发布时间）不算。
- 接口：`GET /api/ingest/data-status`（三类计数与阈值；`?kind=` 分页列出；`?ids=` 取指定几位）、`GET /api/ingest/data-status/:creatorId`（一位博主的全部状态与各来源的未取到次数）。
- 运营端：博主列表每行按 `?ids=` 标「有新数字，可重新发布」「平台上已找不到」；详情页顶部说明哪些指标变了（先下架再重新发布），被标「平台上已找不到」时给「还在，恢复显示」（`keep`）与「确认已不在」（`gone`）两个按钮，只有 `ingest.write` 能点。

## 趋势：按来源分线、对数粉丝斜率、人话提示

`apps/api/src/ingest/trends.ts`，接口 `GET /api/ingest/trends/:creatorId`。

- **不混来源**：每个来源一条线（蒲公英 68 万与千瓜 53 万画在一条线上会看成掉粉 22%）；`primarySource` 是份数最多的来源，界面默认画它。
- **粉丝斜率**：对 ln(粉丝) 与天数做最小二乘直线，斜率 `perDay` 即每天的平均增长率，`growth30d` = e^(30·perDay) − 1（「按这个速度一个月大约 +4%」），`r2` 表示直线拟合得多好。少于 3 份或跨度不足 7 天不算。
- **人话提示**（只提示，不参与排序、不改任何数字）：同一来源相邻两份间隔 ≤ 14 天、粉丝变动 ≥ 20% → 「某日前后 N 天内粉丝涨了 / 掉了 X%」（各取最大的一次）；互动率 ≥ 同来源、同统计窗口、同量级博主中位数的 3 倍且该组 ≥ 30 人 → 「互动率是同量级博主一般水平的 N 倍」；跨度 ≥ 14 天粉丝涨 ≥ 5% 而互动中位数降 ≥ 20% → 「粉丝在涨，互动却在降」。文案三语（`messages`），参数在 `params`。阈值可用 `TREND_CONFIG`（JSON，如 `{"jumpRatio":0.3}`）改。
- 同组中位数取博主表里最近一次来源为该来源的博主的最新数字。

## 失败：先分清值不值得重试

| 情况 | 判断 | 动作 |
|---|---|---|
| 平台 5xx / 429 | 暂时性（`SOURCE_UNAVAILABLE`） | 带随机抖动的指数退避（见下），最多 `max_attempts`（默认 3）次 |
| 单次调用超时 | 暂时性（`VENDOR_TIMEOUT`） | 同上退避；错误信息注明「may have been billed」，这次调用记为「可能已扣费」（`maybe_billed`），金额照记 |
| 402 余额不足 | 永久（`BALANCE_EXHAUSTED`） | 任务进搁置记录（可重放）；**来源暂停**（`ingest_sources.paused_at`），worker 不再领这个来源的任务，已在跑的任务下一次调用前停下并重新排队；运维端首页出提醒卡片，审计记 `source.paused`（操作人为空 = 系统）。充值后在首页点「恢复抓取」（`POST /api/dev/sources/:id/resume`，审计 `source.resumed`），再重放搁置记录 |
| 401 凭证失效 | 永久（`CREDENTIAL_INVALID`） | 第一次就停；不暂停来源（换 key 后直接重放） |
| 400 | 先重发一次（蒲公英，只在同一次调用里） | 第二次仍 400 → `VENDOR_REJECTED` 永久 |
| 其它 4xx（403 / 404 / 422） | 永久（`VENDOR_REJECTED`） | 第一次就停，不空转 |
| 200 但内层 `success=false` / 业务 code 非成功 | 永久（`VENDOR_INNER_ERROR`） | 不重试（已计费，重试只会再扣一次）；补全段落遇到时只丢这一段并记一条说明 |
| 接入信息不全、未知来源、返回结构里没有记录列表 | 永久 | 第一次就停，不空转 |

判断在 `classifyIngestFailure()`，错误信息写库前过一遍脱敏（`token=***`），凭证不会进数据库也不会上界面。

退避用 full jitter：第 n 次失败后在 [0, min(上限, 基数 · 2ⁿ)) 里均匀取一个等待时间（默认基数 1 秒、上限 5 分钟，即第 1 次 0–2 秒、第 2 次 0–4 秒），许多任务同时失败时不会约好一起再撞过去。供应商回了 `Retry-After`（秒数或 HTTP 日期）时它是下限：至少等那么久，最多按 `INGEST_RETRY_AFTER_CAP_MS`（默认 1 小时）封顶。参数 `INGEST_BACKOFF_BASE_MS` / `INGEST_BACKOFF_CAP_MS` / `INGEST_RETRY_AFTER_CAP_MS`。

## 搁置记录（死信队列）

没能完成的东西一律留档，不静默丢弃。两类，且只有这两类：

| 类型 | 什么时候产生 | 留下什么 | 重放做什么 |
|---|---|---|---|
| `job`（整次抓取） | 重试用尽，或永久失败 | `query` + `cursor` + 次数 | 按原参数从游标**续跑**，新建一个任务并回填 `replay_job_id` |
| `record`（单个博主） | 某条读不出来（`RECORD_INVALID`）或写不进去（`RECORD_WRITE_FAILED`） | 平台原始 JSON | 用留下的 JSON 重读入库，**不打平台、不计配额** |

- 队列自己永远不会重放搁置记录：能成功的前提是有人改了东西（凭证、字段对应关系、平台那边恢复），自动空转只会烧钱。
- 同一条博主反复失败只更新那一条（`(source, external_id)` 上的部分唯一索引），不堆重复；`attempts` 记累计次数。
- 重放失败会把 `replay_count` 加一并留在待处理里；到 `DEAD_LETTER_MAX_REPLAYS`（3）次界面不再提供「再试一次」，先去改设置。
- 运维端直接点任务「重试」时，这个任务的搁置记录会一起结掉（`state = replayed`，指向同一任务），不留孤儿。
- 表：`ingest_dead_letters(kind, state, source, job_id, external_id, code, message, attempts, replay_count, query, cursor, payload, replay_job_id, resolved_at, resolved_by)`。
- 接口：`GET /api/dev/dead-letters?state=&kind=&source=`、`GET /api/dev/dead-letters/:id`、`POST .../replay`、`POST .../dismiss`（看需要 `dev.read`，处理需要 `dev.retry`）。`GET /api/dev/health` 带 `deadLetters` 计数与当前在抓的来源。
- 界面上叫「搁置记录」，不说「死信」：一张表列出类型、人话原因、试过几次，右侧「再试一次 / 不再处理」。

## 保留期限：现阶段全部保留

**现阶段所有数据都保留，默认不删任何东西**（用户决定）。清理代码仍在，但每一类都要运维显式设成正数才会执行；不设 = 这一类全留。

打开任一类后，抽水进程（抢到 `INGEST_QUEUE_LOCK` 的那个）按 `RETENTION_INTERVAL_HOURS`（默认 24）清一次，抢到锁后先清一次；锁只有一把，所以全集群同一时刻只有一个进程在删。每类分批删（每批 5000 行），第一次清很久没清过的库也不会长时间锁表。

| 数据 | 默认 | 打开方式（正数才生效；`0` 或不设 = 全留） |
|---|---|---|
| `creator_raw` 平台原始 JSON（每次抓取一行；内容相同的原文在 `raw_payloads` 只存一份，属无损去重） | 全留 | `RETENTION_RAW_PER_SOURCE=N`：每个（博主，来源）只留最新 N 条，随后删掉没人再指向的 `raw_payloads` |
| `ingest_dead_letters` 已处理（`replayed` / `dismissed`） | 全留；待处理的无论如何都不删 | `RETENTION_DEAD_LETTER_DAYS=N`：结掉后 N 天（按 `resolved_at`） |
| `audit_logs` | 全留 | `RETENTION_AUDIT_DAYS=N` |
| `ingest_jobs` 已结束的抓取任务（`ok` / `failed`） | 全留 | `RETENTION_JOB_DAYS=N`：结束（`ended_at`）超过 N 天的。以下永远不删：还有待处理搁置记录的、仍被某位博主记为「第一次带进来 / 最近一次写入」的任务、表格导入（批量任务）；排队中 / 进行中 / 等配额的任务也不在范围内。快照上的 `job_id` 只是文字，任务删了快照照样在 |
| `creator_metrics_history` 历史快照 | 永久，不参与清理（趋势线靠它，平台补不回来）；每人每源每天只有一份，当天再抓是覆盖写 | — |

`RETENTION_INTERVAL_HOURS=0` 关闭整个检查。每次清完写一行 JSON 日志 `retention.sweep`，带各类删了多少；失败写 `retention.failed`，不影响抽水。实现在 `apps/api/src/ingest/retention.ts`。

## 转换层约束

- 取不到的数字保持 `null`，界面显示"—"。不用默认值、不推测。
- 数字写法统一走契约 `parseNumber()`：`万/萬/w`、`亿/億`、`千/k`、`M/百万`、韩文 `천/만/억`、千分位逗号、全角数字、负号（含 `−` U+2212、全角 `－`）、科学计数法；单位按十进制换算（`0.07万` 恰好是 700，不会出现 700.0000000000001）。`10万+` 取下限并记 `lowerBound`；`5000-8000` 这类区间、`—` / `-` / `暂无` 等占位一律 `null` 并记 `range` / `placeholder`；认不出记 `unparseable`。计数字段取整，负数（涨粉除外）或超过 integer 上限（2147483647）记 `outOfRange` 不写入；金额与单价不得为负。警告以 `<字段>.<原因>` 进 `warnings[]`。
- 供应商响应与演示数据先取原文再解析：超过 2^53 的整数（如长 ID）保留原文数字串，不会被四舍五入成同一个 ID。
- 取值时占位符算缺失：`{粉丝数: "-", fans_count: 5000}` 取到 5000，不会被 `-` 挡住。
- 中位数 / 报价 / 单价（`ZERO_MEANS_HIDDEN_KEYS`）为 `0` 表示"未展示"：三个来源和表格导入一律按 `null` 处理并记 `<字段>.notShown`，不会以 CPE=0 排进前 10%；某个别名是 0 时继续看下一个别名。笔记数、涨粉的 0 是真实的 0，照写。
- 比率的单位逐字段声明，不按数值大小猜：`percent` 字段 `"91"` / `0.8` 分别是 91% / 0.8%，`ratio` 字段 `0.91` 是 91%、`1.2` 就是 120%；带 `%` / `％` 的字串一律按百分数。千瓜 `粉丝真实度`/`爆文率`、新红 `粉丝真实度`/`互动粉丝比`、蒲公英各 `*Rate` 为 `percent`，蒲公英 `pagePercentVo` 为 `ratio`。`<来源>_FIELD_MAP` 可写 `{"paths": [...], "unit": "percent"}` 改单位，只给路径则沿用默认单位。占比类字段（读者粉丝比、活跃粉丝比、互动粉丝比、完播率、爆文率、种草评论比、流量来源、粉丝真实度）超出 0–1 记 `outOfRange` 不写入。
- 健康等级只有两级（蒲公英 2024-09 起「健康 / 异常」，每月 1 日评定）：`toHealthLevel()` 把「健康 / 正常 / 优秀 / 良好 / 普通」都认作健康、「异常」认作异常，`metrics.health` 只会是 `healthy` / `abnormal` / `null`（与契约 `HEALTH_GRADES` 相同；迁移 `0043` 把存量里残留的 `excellent` / `normal` 改标为 `healthy`，发布快照不动）。低活跃是另一件事：蒲公英 `lowActive` 同时写进 `signals.lowActive` 与 `metrics.lowActive`，不再推成健康等级；蒲公英接口里没有确认过的健康等级字段，所以蒲公英博主的 `health` 暂为 `null`（待实测）。按健康筛选时，「异常」与「低活跃」一起算作要排除的一类（与蒲公英 `excludeLowActive` 一致）。
- 共享指标装不下、或不能混在一起的来源事实放在 `signals`（契约 `SourceSignals`，键名与线 A 契约的指标同名：`completionRate`、`read3sRate`、`fanInteractionRatio`、`storeVisitUnitPrice`、`platformRanks`、`lowActive`，合并后可直接搬进指标；存 `creators.source_signals` 与每条快照的 `creator_metrics_history.signals`）：健康等级、低活跃、近 7 天是否活跃、视频完播率与图文 3 秒阅读率（分开两个字段，也写进指标 `completionRate` / `read3sRate`）、合作笔记总数（`coopNoteCount` 只取近 30 天 `coopNoteNum30d`，不再拿累计的 `businessNoteCount` 兜底）、新红「互动粉丝比」（口径未公开，不再写进蒲公英的 `engagedFanRatio`）、蒲公英「超过 X% 同类博主」各项（`platformRanks`，0–1）、外溢进店 UV 中位数与外溢进店单价（字段名 `mCpuvNum` / `estimateCpuv*` 待实测），以及各字段实际覆盖的天数（`windowDays`：活跃粉丝占比 28 天，涨粉、互动 / 阅读粉丝占比、合作笔记与外溢进店 30 天；90 天窗口的记录不拿 30 天值兜底，见 03「90 天窗口不回落到 30 天值」）。
- 派生比率（`readToFollowerRatio`、`collectLikeRatio`、`engagementRate` 缺失时用 中位数相除）在 `deriveMetrics()` 统一算，适配器不算。
- 转换层每个字段带 `warnings[]`（缺失 / 供应商估算），存在 `NormalizedCreator`，运营端原始数据抽屉可见。

## 入库：只有一处

博主进库只有一个函数：`upsertCreatorFromNormalized()`（`apps/api/src/ingest/persist.ts`）。队列翻到的一页、搁置记录的重放、运营上传的表格，三条路都调它，所以行为一致：

| 做什么 | 规则 |
|---|---|
| 找人 | 有小红书号时先按号找：号的主人优先（这条记录的来源链接移过去，原先那位的原始 JSON 与快照不动）；否则依次 `creator_sources(source, external_id)` → `creator_key`；都没有才新建 `draft`。两个写入同时新建同一个号时，后到的重试一次并落到先到的那位上 |
| 写什么 | 最新数字（`metrics`、`followers` …）+ `needs_review = true`。`status`、`metrics_locked`、`metrics_locked_at`（发布快照）**永远不碰**，只有发布会动 |
| 空值 | 这次没带的粉丝数 / 地区 / 领域 / 小红书号保留原值，不被抹掉 |
| 附带记录（仅来自数据源的） | `creator_sources` 链接、`creator_raw` 原样 JSON、一条 `creator_metrics_history` |
| 表格行 | 只带粉丝与图文报价，只改这两项（其余平台指标保留）；不写历史快照（人填的数不是平台测量），原文件留在对象存储 `batches/<任务 id>/`。新建的博主带「没合作过的」、报价与一条待校对审核。数字与数据源同一个解析器（`1.2万`、`1.2E+7` 都认）；`暂无` / `-` 记为未知；区间（`5000-8000`）、负数、认不出的写法整行进搁置记录，不写成错数。同名不同人不合并：没有 `userId` / 小红书号的行各自新建，不拿昵称当身份。表格按真正的 XML 读：`<c .../>` 这类带样式的空单元格、省略 `r` 的单元格都不会让后面的列错位 |
| 失败 | 每个博主一个事务，中途失败什么都不留；来自数据源的那条与表格行都进搁置记录（`RECORD_INVALID` / `RECORD_WRITE_FAILED`），表格行另计入 `failedCount`。表格行的搁置记录 `source = file-drop`、`externalId = <任务 id>#<行号>`，`payload` 是那一行的单元格（带文件名），重放时按同样规则重读，不需要原文件 |

开任务只有两个入口：`POST /api/ingest/fetch`（数据源，走队列、扣配额、限速）与 `POST /api/ops/batches`（表格，必须带文件）。旧的 `POST /api/ingest/jobs` 已下线（410）：它绕过队列当场跑，数据源不是适配器时还会凭空造一个「投递达人」。

## 身份归并

蒲公英给 `redId`（小红书号），千瓜 / 新红导出通常也带小红书号。归并只认小红书号，不认昵称（同一来源的同一 id 先按 `creator_sources` 认，见上表）。供应商 id 只在本供应商内唯一：`creator_key` = `<来源>:<id>`（如 `qiangua:10001`），没有小红书号的记录 `xhs_id` 留空、不拿供应商 id 充数，所以千瓜 10001 与新红 10001 是两个人。小红书号只有一种写法：去首尾空白（含全角空格）、全角转半角、小写（`"Cheongdam_Skin "` 与 `"cheongdam_skin"` 是同一个号），契约 `normalizeXhsId()` 与数据库触发器 `kcs_normalize_xhs_id` 规则相同，一个号只属于一个博主（唯一索引）。迁移 `0042` 把存量里只差写法的博主合并：已上架的（其次有发布快照的、再其次最早的）留下，其余所有关联行移过去，被并掉的行与移不过去的重复关联原样留在 `creator_merges`。迁移 `0040` 把旧规则误合并的博主按各链接原始 JSON 里的小红书号拆开（最早那条链接留在原博主上，其余拆成新的草稿并带走自己的原始 JSON、快照与链接）。归并后：

- `creators` 一条；`creator_sources` 每个来源一条链接；
- `creator_metrics_history` 里两源的快照并存，`source` 不同；
- 分位仍按 `source × tier` 分组计算，不跨源比较；
- 选人端详情页"数据来源"卡列出所有链接与最后抓取时间。
