## 二、项目概述与关键需求

### 2.1 项目定位

面向韩国品牌的**达人（Influencer）数据统一管理与合作决策系统**。核心价值是把来自不同渠道的达人信息，转化为可筛选、可解释、可复核、可追踪、可导出的业务决策资料。

### 2.2 六大功能模块

| 编号 | 模块 | 核心能力 | 复杂度 |
|------|------|---------|--------|
| M1 | 导入与数据清洗 | 外部数据统一入库，批次管理，字段校验，异常记录 | 中 |
| M2 | 达人列表与批量筛选 | 按时间/来源/平台/标签/指标多维度筛选 | 中低 |
| M3 | 批次分析与对比范围 | 全局分析、本批次分析、指定范围分析；分析任务版本管理 | 中高 |
| M4 | AI 分析强化 | 达人定位、适配场景、风险提示、联系切入点、人工确认项 | 高 |
| M5 | 人工复核与规则复盘 | 标准化复核→分歧统计→规则建议→历史回放→规则版本管理 | 高 |
| M6 | 联系 SOP、报价与报告 | 联系状态跟踪、多级报价管理、报告导出 | 中 |

### 2.3 明确排除范围（V2 不做）

- 不实现完整 AI Marketing OS
- 不承诺多平台持续自动采集
- 不实现自动登录/自动联系/自动私信
- 不做未经验证的粉丝画像、假粉判断、销量预测、ROI 归因
- 不以 AI 输出为最终决策
- 不在代码仓库保存真实客户数据

这些排除项的明确列出极大地降低了 V2 的范围风险和合规风险。

## 三、技术可行性分析

### 3.1 架构可行性

系统本质是一个 **Web 应用 + 数据库 + AI 调用 + 报表导出** 的经典三层架构：

```
┌──────────────────────────────┐
│    前端 (Web UI)              │
│  达人列表 / 分析看板 / 复核面板 │
├──────────────────────────────┤
│    后端 API                   │
│  导入/清洗/筛选/分析/复核/报告  │
├──────────────────────────────┤
│    数据层                     │
│  达人库 / 批次 / 规则 / 复核记录│
│  AI 服务集成                  │
└──────────────────────────────┘
```

**评估**：每层均有成熟技术方案，无技术壁垒。

### 3.2 各模块技术分解

#### M1 导入与数据清洗（复杂度：中）

- **核心挑战**：字段格式不统一、缺失值处理、多来源映射
- **可行方案**：定义标准数据模型 → 字段映射配置 → 数据校验规则 → 异常记录入库
- **关键技术**：CSV/Excel 解析、数据校验框架、ETL 轻量管道
- **可行性**：**高**。这是成熟的 ETL 范式，技术风险低。

#### M2 达人列表与批量筛选（复杂度：中低）

- **核心挑战**：多维度组合筛选的性能
- **可行方案**：数据库索引 + 分页查询 + 前端筛选组件
- **关键技术**：数据库查询优化、前端表格/筛选组件
- **可行性**：**高**。CRUD + 筛选是 Web 开发基本能力。

#### M3 批次分析与对比范围（复杂度：中高）

- **核心挑战**：不同对比范围的计算逻辑、分析任务版本管理、结果可追溯
- **可行方案**：将每次分析建模为 `AnalysisRun`（分析任务），记录规则版本、对比范围、时间戳，结果不可变追加
- **关键技术**：规则引擎、任务队列、版本化存储
- **可行性**：**高**。涉及一定设计复杂度，但技术上完全可行。

#### M4 AI 分析强化（复杂度：高）

- **核心挑战**：AI 输出的可靠性、可解释性和一致性
- **可行方案**：结构化 Prompt 模板 + 多维度输出约束（定位、场景、风险、切入点、确认项）+ 输出格式校验
- **关键技术**：LLM API 集成（GPT/Claude 等）、Prompt Engineering、结构化输出解析
- **可行性**：**高**。现有 LLM 能力足以支撑达人分析（文本理解 + 结构化输出）。主要风险在 AI 质量而非技术可行性。

#### M5 人工复核与规则复盘（复杂度：高）

- **核心挑战**：如何让离散的人工判断形成可计算的规则反馈
- **可行方案**：
  1. 标准化复核选项（推荐/不推荐 + 分歧原因分类）
  2. 分歧原因→规则策略的映射表
  3. 规则版本化（每次规则变更创建新版本）
  4. 历史回放（用旧规则版本重新计算历史数据，验证新规则效果）
- **关键技术**：规则引擎版本管理、统计聚合、历史数据回放
- **可行性**：**中高**。这是整个系统最有设计难度的模块，但核心逻辑可分解为"分类统计 + 规则映射"。

#### M6 联系 SOP、报价与报告（复杂度：中）

- **核心挑战**：多级报价（参考报价/询价报价/最终报价）、报告模板设计
- **可行方案**：状态机管理联系流程，报价分级存储，报告模板 + 数据填充
- **关键技术**：状态机、模板引擎、导出（PDF/Excel）
- **可行性**：**高**。典型的业务记录 + 报表导出模式。

### 3.3 技术可行性总结

| 评估维度 | 评级 | 说明 |
|---------|------|------|
| 技术成熟度 | ★★★★★ | 所有模块均可使用成熟技术栈实现 |
| 技术壁垒 | ★☆☆☆☆ | 无核心技术壁垒，主要在工程设计和 AI Prompt 质量 |
| 技术风险 | ★★☆☆☆ | M4/M5 的 AI 质量和规则引擎设计有一定风险，但可控 |
| 可扩展性 | ★★★★☆ | 模块化设计便于后续扩展 V3/V4 能力 |

**结论：技术完全可行。**

## 五、推荐技术栈

### 5.1 推荐方案

| 层级 | 推荐技术 | 备选方案 | 选择理由 |
|------|---------|---------|---------|
| 前端 | **React + Ant Design** | Vue + Element Plus | 组件丰富，表格/筛选/表单能力强 |
| 后端 | **Python (FastAPI)** | Node.js (NestJS) | AI 集成便利，数据处理生态好 |
| 数据库 | **PostgreSQL** | MySQL | JSON 字段支持好，适合灵活达人数据 |
| ORM | **SQLAlchemy** | Prisma | Python 生态首选 |
| AI 服务 | **OpenAI API / Claude API** | 本地模型 | 质量稳定，Prompt 可调 |
| 任务队列 | **Celery + Redis** | RQ | 分析任务异步化 |
| 报表导出 | **openpyxl + WeasyPrint** | Pandoc | Excel + PDF 双格式 |
| 版本管理 | **Git (私有仓库)** | - | 计划书明确要求 |
| 部署 | **Docker + Nginx** | 云服务 | 便于交付和演示 |

### 5.2 技术选型理由

选择 Python + React 组合的核心原因：

1. **AI 集成零摩擦**：LLM SDK 以 Python 为第一语言，Prompt 调试和结构化输出处理更自然
2. **数据处理能力强**：pandas、openpyxl 等库可轻松处理 Excel/CSV 导入清洗
3. **FastAPI 性能足够**：对于数据管理和报表系统，异步支持和高并发不是瓶颈
4. **React 生态成熟**：Ant Design Pro 提供开箱即用的表格/筛选/表单组件

两人分工的优点：
- 主系统和数据适配**解耦**，边界清楚

- 各自可独立开发，降低协作成本

潜在不足：
- 所有核心业务逻辑集中在 1 人身上，存在**关键人风险**
- 数据适配方进度可能影响主系统测试

支撑结论的关键论据：

1. **范围收敛得当**：从"完整 AI Marketing OS"主动收敛为"达人数据管理与合作决策系统"，避免了常见的范围蔓延导致的项目失败。
2. **技术零壁垒**：所有模块均可用成熟技术栈实现，核心挑战在设计（规则引擎、AI Prompt）而非实现。
3. **风险已充分识别**：9+3 个风险点均有对应策略，大多数风险影响可控。
4. **闭环完整可演示**：6 个模块形成"导入→筛选→分析→复核→联系→报告"的完整业务闭环，每个阶段都可独立演示和验收。
5. **团队分工清晰**：主系统与数据适配解耦，通过标准数据格式对接，降低协作成本。

### 9.3 成功的关键条件

1. **严格范围控制**：任何 V2 范围外的需求记录为 V3，不在当前阶段实现。
2. **真实数据样例尽早到位**：阶段一的核心依赖，建议项目启动第一周就推动获取。
3. **AI Prompt 迭代需要真实业务反馈**：AI 分析质量需要与真实韩国品牌达人合作场景反复校准。
4. **规则复盘逻辑是核心难点**：需要在阶段三投入最多设计和验证精力。
