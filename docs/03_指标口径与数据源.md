# 指标口径与数据源

系统不计算综合分、推荐等级或关键词权重。采集任务接收参数化查询，由数据源适配器拉取原始 JSON；原始响应原样保存在 `creator_raw`，转换层再写入统一的 `CreatorMetrics`。筛选、排序和高亮通过可保存的 `SavedQuery` 表达。

## 数据源与路线

| 数据源 | 路线 | 接入方式 | 文档状态（2026-09 核查） |
|---|---|---|---|
| 蒲公英 | A：小红书官方博主数据 | `PGY_GATEWAY=official` 官方开放平台（ad-market.xiaohongshu.com，文档中心需合作方登录）；`tikhub`（api.tikhub.io，Bearer，POST JSON）；`justoneapi`（api.justoneapi.com，`token` 查询参数，GET）。三者转发的都是蒲公英 `solar` 原样 JSON，共用一套字段映射 | 字段已按公开的 TikHub / JustOneAPI OpenAPI 描述与多份公开样例响应核对，见下表 |
| 千瓜 | B：第三方数据供应商 | 企业合同开通后由商务下发接口与 Token；`QIANGUA_BASE_URL` + `QIANGUA_SEARCH_PATH`，字段用 `QIANGUA_FIELD_MAP`（JSON）覆盖 | 官网无公开 API 文档，字段表随合同交付 |
| 新红（新榜） | B：第三方数据供应商 | 新榜数据 API：`api.newrank.cn`，请求头 `Key: <apiKey>`，表单编码 POST，接口路径在付费控制台（新榜官网 → 数据API）复制到 `XINHONG_SEARCH_PATH`；字段用 `XINHONG_FIELD_MAP` 覆盖 | 接口列表与字段在付费控制台内，不公开 |

系统没有路线 C，不进行自建抓取。未配置 Token 时，后端只返回明确标记为 `fixture` 的样例数据（字段名与真实响应一致），供本地开发和演示。

## 蒲公英接口与字段映射

### 用到的接口

| 用途 | 蒲公英 solar 路径 | TikHub | JustOneAPI |
|---|---|---|---|
| 找博主列表 | `POST /api/solar/cooperator/blogger/v2` → `data.kols[]`（每条约 140 字段） | `POST /api/v1/xiaohongshu/pgy/get_blogger_list` | `GET /api/xiaohongshu-pgy/api/solar/cooperator/blogger/v2/v1` |
| 博主资料 | `GET /api/solar/cooperator/user/blogger/{userId}` | `get_blogger_detail` | `.../cooperator/user/blogger/userId/v1` |
| 数据概览 | `GET /api/solar/kol/dataV3/dataSummary?userId&business=0` | `get_blogger_data_summary` | `.../kol/dataV3/dataSummary/v1` |
| 粉丝概览 | `GET /api/solar/kol/dataV3/fansSummary?userId` | `get_blogger_fans_summary` | `.../kol/dataV3/fansSummary/v1` |
| 笔记表现 | `GET /api/solar/kol/dataV3/notesRate?userId&business=0\|1&noteType=3&dateType=…&advertiseSwitch=1\|0` | `get_blogger_notes_rate` | `.../kol/dataV3/notesRate/v1` |
| 粉丝画像 | `GET /api/solar/kol/data/{userId}/fans_profile` | `get_blogger_fans_profile` | `.../kol/data/userId/fans_profile/v1` |

- `dateType`（**待实测**）：网关文档写 `1` = 近 30 日、`2` = 近 90 日，`3` 会被拒（422）；官方与 TikHub 同值；JustOneAPI 要字符串枚举 `DAY_30` / `DAY_90`。当前按此发送：`window=30` → `1` / `DAY_30`，`window=90` → `2` / `DAY_90`。实测方法：同一博主分别请求 1 / 2，对比 `noteNumber`。环境变量 `PGY_DATE_TYPES`（JSON，如 `{"30":1,"90":2}`）可覆盖；实际发出的值记在原始 JSON 的 `kcsDateType`，核定后可按原文重算。
- **取数口径**（每个来源可配）：`advertiseSwitch` / `advertise_switch`：`1` 全部流量（含薯条等投放加热）、`0` 仅自然流量；`business`：`0` 日常笔记、`1` 合作笔记（数据概览与笔记表现都带，平台的预估单价也随之变）。默认 **全部流量 · 日常笔记**，改法：`ingest_sources.traffic_scope`（`all` / `organic`）与 `business_scope`（`daily` / `coop`），环境变量 `PGY_TRAFFIC_SCOPE` / `PGY_BUSINESS_SCOPE` 优先；写错的值跳过。用的口径记在原始 JSON 的 `kcsScope` 和指标的 `basis.trafficScope` / `basis.businessScope`；选人端博主详情在窗口旁显示「全部流量 · 日常笔记」，受口径影响的指标（`SCOPED_METRIC_KEYS`：各中位数、互动率、完播 / 3 秒阅读、发文、爆文、流量来源、单价）说明里注明口径，运维端「调用与额度」显示每个来源当前口径与来源（环境变量 / 来源设置 / 默认）。没带 `kcsScope` 的旧记录与演示数据不显示口径，不猜。
- 列表接口的 `total` 恒为 5000，是翻页上限而不是命中数；`page_size` 固定 20，`page_num` 1–250。`cursor` 即页码。
- 按 `externalIds` 刷新时每个博主拉资料 + 4 个数据接口并合并到同一条 `payload`（`dataSummary` / `fansSummary` / `notesRate` / `fansProfile`）。
- **90 天窗口不回落到 30 天值**：列表字段（`clickMidNum`、`readMidCoop30`、`estimatePictureCpm`…）与数据概览都是近 30 天。`window=90` 的记录里，跟着窗口走的数（曝光 / 阅读 / 互动中位数、发文、爆文、完播率、流量来源、`*BeyondRate` 排位）只取按 90 天请求回来的 `notesRate`，缺就空着；合作笔记中位数和平台预估单价（CPR / CPE / CPM）也不取，单价改由 90 天中位数按「派生比率」自算（`basis` 写明公式）。固定窗口的粉丝事实照常写入并在 `windowDays` 记天数：涨粉 30 天、活跃粉丝 28 天、互动 / 阅读粉丝 30 天、合作笔记数 30 天、外溢进店 30 天。没做补全的搜索结果没有 `kcsWindow`，一律记为 30 天。搜索时默认只存列表字段，`PGY_ENRICH=1` 才逐个补全（付费网关按次计费，200 响应即扣费，空结果也扣）。
- 原始响应中的中位数、报价、单价为 `0` 表示"未展示"，转换层按 `null` 处理。

## 派生比率

转换层（契约 `deriveMetrics`）只计算可由原始字段直接复算的比率；供应商已经提供该字段时保留供应商值。派生值**存原始精度**（显示时才舍入），算出来的键记在 `derived[]`，所用公式记在 `basis`（如 `cpe: "priceImage/coopInteractionMedian"`），以后换口径能分辨哪些是自算的。

| 指标 | 公式 |
|---|---|
| CPE `cpe` | 图文报价 ÷ 合作互动中位数（无则日常互动中位数）。**不再**拿视频报价顶替 |
| 视频 CPE `cpeVideo` | 视频报价 ÷ 合作互动中位数（无则日常互动中位数），与图文分开排位 |
| 每次阅读成本 `cpr`（原 `cpv`） | 图文报价 ÷ 合作阅读中位数（无则阅读中位数） |
| 千次曝光成本 `cpm` | 图文报价 × 1000 ÷ 曝光中位数。按阅读算出的旧值不是 CPM，读入时丢弃 |
| 千次阅读成本 `cpmRead` | 图文报价 × 1000 ÷ 合作阅读中位数（无则阅读中位数） |
| 互动率 | 互动中位数 ÷ 阅读中位数 |
| 收藏赞比 | 收藏中位数 ÷ 点赞中位数 |
| 读粉比 `readToFollowerRatio` | 阅读中位数 ÷ 粉丝数 |
| 涨粉率 | 涨粉 ÷（当前粉丝数－涨粉）；**分母 ≤ 0 为空**（粉丝从 0 起涨或数据矛盾时不给无穷大） |
| 爆文率 | 爆文数 ÷ 近 30 天发文数 |

分母为 0、缺失或非有限数时结果为 `null`。旧记录里按 2–4 位小数舍入存下的派生值，读入时认出来并按原始精度重算。

### 指标方向

每个指标在契约 `METRIC_FIELDS` 里有 `better: 'high' | 'low' | null`。`null` 的只描述、不排位、不参与「好 / 差」高亮：

- 粉丝数、发文数、报价（量本身没有好坏）；
- 阅读粉丝占比 `readFanRatio`、搜索 / 推荐 / 关注流量占比（三者加起来约为 1，高低取决于投放目的）；
- 新红「互动粉丝比」`fanInteractionRatio`（无公开定义）、外溢进店单价 `storeVisitUnitPrice`（高低都说得通）、合作笔记数。

求购评论占比 `purchaseIntentCommentRatio` 目前没有来源，界面隐藏（`hidden`），等有真实字段再放出。

### 金额与币种

- 手填报价（`prices`）按币种最小单位存 `bigint`（`amount_min_minor` / `amount_max_minor`：人民币 / 美元是分，韩元是원），币种只收大写 `CNY` / `USD` / `KRW`（迁移 `0022`；旧整数列变成只读的生成列）。
- 非人民币报价**只有**记录了汇率（`fx_to_cny` + `fx_recorded_at`）才折成人民币进 `priceImage` 与各项成本；没有汇率时成本留空，不把 500 万韩元当 500 万元。折算时用的原币种与汇率记在 `metrics.priceQuote`。
- 写接口里的指标一律是有限 JSON 数字或 `null`（`z.number().finite().nullable()`）：`"12"`、`1e400` 都是 400。

### 服务费

成本默认按平台报价、**不含**服务费显示。方案可选 `serviceFee`：`0`（默认）/ `0.1`（蒲公英普通）/ `0.2`（优效模式），选了就把报价与按报价算的单价都乘上 (1 + 费率) 再筛选、排序和排位。蒲公英自带的 CPM / CPE 是否已含服务费**待核定**。

## 粉丝层级

| 层级 | 粉丝数 |
|---|---|
| 头部 `head` | 大于等于 50 万 |
| 腰部 `mid` | 5 万（含）至 50 万 |
| 初级 `junior` | 5 千（含）至 5 万 |
| 素人 `amateur` | 300（含）至 5 千 |
| 未知 `unknown` | 缺失或低于 300 |

边界在代码中按下限包含处理，因此 50 万属于头部，5 万属于腰部，5 千属于初级，300 属于素人。层级用于显示、筛选与参考线分组；**排位不再按层级硬切**（见下）。

## 同类分位

「好不好」一律说成在同类博主里排第几（契约 `cohort.ts`，参数常量 `COHORT_RULES`）。

**和谁比**

- 分组 = 来源 × 统计窗口（30 / 90 天）× 主要内容形式（图文 / 视频）；没有来源或形式的自成一组。组键写作 `source|window|form`（缺失写 `-`），如 `pugongying|30|image`。
- 组内每个指标单独找邻居：按 log10(粉丝数) 取离得最近、且该指标有值的博主，往外扩到凑够目标人数为止，但粉丝跨度**不超过一个数量级**（一个层级的宽度）。所以 4.9 万和 5.1 万粉的博主可以互相比较，不会被层级边界切开。
- 发布快照里的数字抓取时间超过 **60 天**的，既不参与比较也不给排位（显示「数据已超过 60 天，暂不排位」）。

**样本量决定说多少**

| 可比人数 | 给出 |
|---|---|
| 少于 10 | 不排位 |
| 10–29 | 三档：`front` 前段（≥ 66.7）/ `middle` 中段 / `back` 后段（< 33.3） |
| 30 及以上 | 五档：`top10`（≥ 90）/ `top25`（75–89.9）/ `upper`（50–74.9）/ `lower`（25–49.9）/ `bottom`（< 25） |

目标人数按来源用自助法（bootstrap）估计：对 25 / 50 / 75 分位点各重抽 200 次，取 95% 区间宽度在 ±10 个百分点以内的最小人数，且不少于 30（候选 30、40 … 400）；某来源还没法估计时用正态近似 97。每次全量刷新时重估，结果存 `cohort_calibration`，运维端 `GET /api/dev/cohorts` 可查当前值与依据。

**怎么算**

- 分位 = (比它差的个数 + 相等个数 / 2) ÷ 可比人数 × 100，一位小数、四舍五入，全程整数运算（数据库与契约逐条一致）。
- 低值更好的指标（CPE、CPM、每次阅读成本等）按「比它**贵**的个数」算，舍入与高值指标对称：一个值和它的镜像落在对称的分位上。分位越高永远代表越好。
- 有计数撑着的比率（爆文率 = 爆文数 ÷ 发文数，发文 ≥ 5 篇才排）按 Wilson 下界（z = 1.96）排，所以 2 篇里 1 篇爆文不会排在 100 篇里 20 篇前面。
- 平台自带同类排位（蒲公英 `*BeyondRate` → `platformRanks`）有值时优先用它（`scope: 'platform'`），本库排位仍附在旁边（`library`），界面写「本库」「小红书」说明是和谁比。
- 分位在发布、下架、拉黑时预先算好，存进窄表 `creator_published` 的 `p_*` 列；博主池只读这张表（见 02）。

**参考线**：组内同层级某指标有 ≥ 30 个当前（未过期）值时，记下它的 25 / 50 / 75 分位（`cohort_reference_lines`），方案编辑器填绝对值时点选、详情页展示。

## 默认高亮

新方案的默认高亮全部相对同类，不含任何绝对数字（没有真实样例前不定死阈值）：

| 条件 | 显示 |
|---|---|
| 健康等级「异常」 | 标红，并压掉这一行所有「好」的标记（门槛，不是加权） |
| CPE 分位 ≥ 75（同类最省的 25%） | 好 |
| 互动率分位 ≤ 25（同类最低的 25%） | 提醒 |
| 蒲公英阅读中位数分位 ≥ 50 | 好（只看蒲公英来源） |
| 蒲公英互动中位数分位 ≥ 50 | 好（只看蒲公英来源） |

高亮支持按值（`gte` / `lte`）或按分位（`percentileGte` / `percentileLte`），可用 `sources` 限定来源。没有分位的行（过期、同类太少）不触发分位高亮。后两条是否合适取决于 `*BeyondRate` 的真实取值，**待核定**。

## 健康等级硬门槛

健康等级只有 `healthy`（健康）/ `abnormal`（异常）两级，「低活跃」是单独的 `lowActive` 标记。健康等级不是加权项，而是可直接阻断候选的硬筛选条件：方案可以只允许 `healthy`；`abnormal` 不会因其他指标突出而被「抵消」。

## 发布快照与审计

两份数字，各管一件事：

- **最新**（`creators.metrics`）：每次抓取、死信重放、表格导入、运营手工改动都更新它，并各留一条 `creator_metrics_history`。运营端详情与两端的趋势读它。
- **发布时**（`creators.metrics_locked` + `metrics_locked_at`）：审核通过并发布、或下架后重新发布的那一刻，把当时的最新数字（粉丝、报价已并入）整份复制过来。选人端博主池的筛选、排序、同类分位、项目名单与导出表格一律按它算，抓取永远不写它；已在池中的博主再点发布也不刷新。

选人端实际读的是由发布快照投影出来的窄表 `creator_published`（02 有列说明）：发布 / 下架 / 拉黑在同一事务里写这张表，并在该组的顾问锁（`pg_advisory_xact_lock`）下重算这一组的分位；运营发布后改名字、地区、分类、合作、报价，由触发器同步到窄表，拉黑或移出还会把组标记为待重算（`cohort_dirty_groups`）。窄表随时可以从 `creators` 重建，删掉一行不丢任何数据：

- 进程启动时只补写缺失或重新发布过的行，只重排这些行所在的组与待重算的组（5 万人、无变化时约 0.2 秒）；`KCS_PUBLISHED_FULL_REFRESH=1` 时全部重写并重估各来源目标人数（5 万人约 24 秒）。
- 之后每 6 小时（`KCS_PUBLISHED_REFRESH_MS`）在后台重排**全部**组并重估目标人数：快照随时间过期后要失去排位。

想让池子用上新数字，只有一条路：运营下架、再发布。博主详情（选人端与运营端）把「发布时」与「最新」并排显示，差异一眼可见。每次适配器采集的供应商 JSON 都单独写入 `creator_raw`，用于追溯字段映射和供应商口径变化。
