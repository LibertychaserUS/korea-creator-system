# 指标口径与数据源

系统不计算综合分、推荐等级或关键词权重。采集任务接收参数化查询，由数据源适配器拉取原始 JSON；原始响应原样保存在 `creator_raw`，转换层再写入统一的 `CreatorMetrics`。筛选、排序和高亮通过可保存的 `SavedQuery` 表达。

## 数据源与路线

| 数据源 | 路线 | 接入方式 | 文档状态（2026-09 核查） |
|---|---|---|---|
| 蒲公英 | A：小红书官方博主数据 | `PGY_GATEWAY=official` 官方开放平台（ad-market.xiaohongshu.com，文档中心需合作方登录）；`tikhub`（api.tikhub.io，Bearer，POST JSON）；`justoneapi`（api.justoneapi.com，`token` 查询参数，GET）。三者转发的都是蒲公英 `solar` 原样 JSON，共用一套字段映射 | 字段已按公开的 TikHub / JustOneAPI OpenAPI 描述与多份公开样例响应核对，见下表 |
| 千瓜 | B：第三方数据供应商 | 企业合同开通后由商务下发接口与 Token；`QIANGUA_BASE_URL` + `QIANGUA_SEARCH_PATH`，字段用 `QIANGUA_FIELD_MAP`（JSON）覆盖 | 官网无公开 API 文档，字段表随合同交付 |
| 新红（新榜） | B：第三方数据供应商 | 新榜数据 API：`api.newrank.cn`，请求头 `Key: <apiKey>`，表单编码 POST，接口路径在付费控制台（新榜官网 → 数据API）复制到 `XINHONG_SEARCH_PATH`；字段用 `XINHONG_FIELD_MAP` 覆盖 | 接口列表与字段在付费控制台内，不公开 |

系统没有路线 C，不进行自建抓取。未配置 Token 时，后端只返回明确标记为 `fixture` 的样例数据（字段名与真实响应一致），供本地开发和演示。

## 蒲公英接口与字段映射

### 用到的接口

| 用途 | 蒲公英 solar 路径 | TikHub | JustOneAPI |
|---|---|---|---|
| 找博主列表 | `POST /api/solar/cooperator/blogger/v2` → `data.kols[]`（每条约 140 字段） | `POST /api/v1/xiaohongshu/pgy/get_blogger_list` | `GET /api/xiaohongshu-pgy/api/solar/cooperator/blogger/v2/v1` |
| 博主资料 | `GET /api/solar/cooperator/user/blogger/{userId}` | `get_blogger_detail` | `.../cooperator/user/blogger/userId/v1` |
| 数据概览 | `GET /api/solar/kol/dataV3/dataSummary?userId&business=0` | `get_blogger_data_summary` | `.../kol/dataV3/dataSummary/v1` |
| 粉丝概览 | `GET /api/solar/kol/dataV3/fansSummary?userId` | `get_blogger_fans_summary` | `.../kol/dataV3/fansSummary/v1` |
| 笔记表现 | `GET /api/solar/kol/dataV3/notesRate?userId&business=0&noteType=3&dateType=1|2&advertiseSwitch=1` | `get_blogger_notes_rate` | `.../kol/dataV3/notesRate/v1` |
| 粉丝画像 | `GET /api/solar/kol/data/{userId}/fans_profile` | `get_blogger_fans_profile` | `.../kol/data/userId/fans_profile/v1` |

- `dateType=1` 为近 30 日，`2` 为近 90 日，对应 `window`。
- 列表接口的 `total` 恒为 5000，是翻页上限而不是命中数；`page_size` 固定 20，`page_num` 1–250。`cursor` 即页码。
- 按 `externalIds` 刷新时每个博主拉资料 + 4 个数据接口并合并到同一条 `payload`（`dataSummary` / `fansSummary` / `notesRate` / `fansProfile`）。搜索时默认只存列表字段，`PGY_ENRICH=1` 才逐个补全（付费网关按次计费，200 响应即扣费，空结果也扣）。
- 原始响应中的中位数、报价、单价为 `0` 表示"未展示"，转换层按 `null` 处理。

### 抓取参数 → 蒲公英筛选

| SourceQuery | TikHub 请求体 | JustOneAPI 查询参数 | 官方 / 网页请求体 |
|---|---|---|---|
| `keyword` | `keyword`, `search_type: 1` | `keyword`, `searchType=NOTE` | `keyword`, `searchType: 1` |

| `priceMin/Max` | `coop.pic_price: {min,max}` | `notePrice=min,max` | `estimatePicReadPrice: [min,max]` |
| `category` | `blogger.content_tag: [..]` | `contentTag` | `contentTag: [..]` |
| `region` | `blogger.location: [..]` | `location` | `location` |
| `health` 不含 `abnormal` | `flags.exclude_low_active: true` | `excludeLowActive=true` | `excludeLowActive: true` |
| `cursor` | `page_num` | `page` | `pageNum` |

类目 / 地域取值必须与蒲公英字典完全一致（多一个字返回 0 条而不报错），字典来自 `get_blogger_filter_options` / `content/tag_tree`。

## 千瓜 / 新红字段映射

两家没有公开字段表，适配器保留供应商导出口径的中文列名和常见英文别名作为默认路径；拿到合同接口后把真实路径写进 `QIANGUA_FIELD_MAP` / `XINHONG_FIELD_MAP`（JSON：`{"followers": ["data.fans_count"], ...}`），无需改代码。

| 统一字段 | 千瓜默认路径 | 新红默认路径 |
|---|---|---|
| `followers`, `followerGrowth`, `noteCount`, `viralCount` | 粉丝数 / 涨粉 / 近 30 天发文 / 爆文数 | 粉丝数 / 近 30 天涨粉 / 近 30 天发文 / 爆文数 |
| `*Median` | 阅读/互动/点赞/收藏/评论中位数 | 曝光/阅读/互动/点赞/收藏/评论中位数 |
| `authenticity` | 粉丝真实度 | 粉丝真实度 |
| `engagedFanRatio` | — | 互动粉丝比 |
| `priceImage` / `priceVideo` / `cpe` / `cpm` | 预估报价 / — / CPE / CPM | 图文报价 / 视频报价 / CPE / CPM |
| `vendorIndex` | 千瓜指数（max 1000） | 新红指数（max 1000） |
| `coopBrands`, `health` | 合作品牌 / 健康等级 | 合作品牌 / 健康等级 |

无法从响应读取的数字必须保留 `null`，不得用默认值或推测值补齐。

## 派生比率

转换层只计算可由原始字段直接复算的比率；供应商已经提供该字段时保留供应商值。

| 指标 | 公式 |
|---|---|
| CPE | 图文报价（无则视频报价）÷ 合作互动中位数（无则互动中位数） |
| CPM | 报价 ÷ 合作阅读中位数（无则阅读中位数）× 1000 |
| 互动率 | 互动中位数 ÷ 阅读中位数 |
| 收藏赞比 | 收藏中位数 ÷ 点赞中位数 |
| 读粉比 | 阅读中位数 ÷ 粉丝数 |
| 涨粉率 | 涨粉 ÷（当前粉丝数－涨粉） |
| 爆文率 | 爆文数 ÷ 近 30 天发文数 |

分母为 0、缺失或非有限数时结果为 `null`。

## 粉丝层级

| 层级 | 粉丝数 |
|---|---|
| 头部 `head` | 大于等于 50 万 |
| 腰部 `mid` | 5 万（含）至 50 万 |
| 初级 `junior` | 5 千（含）至 5 万 |
| 素人 `amateur` | 300（含）至 5 千 |
| 未知 `unknown` | 缺失或低于 300 |

边界在代码中按下限包含处理，因此 50 万属于头部，5 万属于腰部，5 千属于初级，300 属于素人。

## 同层百分位

可比较指标只在相同粉丝层级中计算百分位。高值更好的指标直接排名；CPE、CPM 等低值更好的指标反向排名，因此百分位越高始终代表同层表现越靠前。

| 分带 | 百分位 |
|---|---|
| `top10` | ≥ 90 |
| `top25` | 75–89.9 |
| `upper` | 50–74.9 |
| `lower` | 25–49.9 |
| `bottom` | < 25 |

同层有效样本少于 2 个时不生成该指标的百分位。

## 健康等级硬门槛

蒲公英健康等级统一为 `excellent`、`normal`、`abnormal`。健康等级不是加权项，而是可直接阻断候选的硬筛选条件。业务查询可以只允许 `excellent`，也可以显式包含 `normal`；`abnormal` 不应因其他指标突出而被综合分“抵消”。

## 发布快照与审计

两份数字，各管一件事：

- **最新**（`creators.metrics`）：每次抓取、死信重放、表格导入、运营手工改动都更新它，并各留一条 `creator_metrics_history`。运营端详情与两端的趋势读它。
- **发布时**（`creators.metrics_locked` + `metrics_locked_at`）：审核通过并发布、或下架后重新发布的那一刻，把当时的最新数字（粉丝、报价已并入）整份复制过来。选人端博主池的筛选、排序、同量级分位、项目名单与导出表格一律按它算，抓取永远不写它；已在池中的博主再点发布也不刷新。

想让池子用上新数字，只有一条路：运营下架、再发布。博主详情（选人端与运营端）把「发布时」与「最新」并排显示，差异一眼可见。每次适配器采集的供应商 JSON 都单独写入 `creator_raw`，用于追溯字段映射和供应商口径变化。
