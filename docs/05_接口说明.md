# 接口说明

API：Hono，`apps/api`，默认 `:7100`。路径与权限的唯一权威是 `packages/kcs-contract/src/api.ts`（`API` 常量）；黑盒测试 `tests/blackbox` 与前端都从那里取路径。`GET /api/openapi.json` 输出汇总。

状态码约定：401 未登录，403 无权限，404 不存在或不可见，409 冲突，400 参数错误，200 / 201 成功，202 已入队。错误体 `{ error: { code, message } }`。

响应字段一律 camelCase（时间是 ISO 字符串）；只有原样存下的平台返回（`payload`）和任务参数（`query`）保留来源的写法。手工拼的行在契约 `responses.ts` 有类型（`IngestJobView` / `BatchView` / `OpsOverview` / `ReviewView` / `AuditLogView` / `JobSampleView` / `CategoryView` / `ProjectView`），单测 `naming.test.ts` 逐个接口检查没有下划线键。路径用契约 `API` 常量，带参数的用 `apiPath(API.projectGet, { id }, { locale })` 拼（参数自动编码、缺参直接报错）；前端不写 `'/api/...'` 字面量。

### 错误码

| HTTP | `error.code` | 何时 |
|---|---|---|
| 401 | `AUTH-LOGIN` | 没带或带了失效的会话 |
| 403 | `AUTH-DENIED` | 有会话但角色不够，或账号没有 KCS 分工；改别人筛选方案的可见范围（`owner_only`） |
| 400 | `VALIDATION` | 请求体不是合法 JSON（`message: invalid_json`）；或字段不合规（`invalid_body` 等），此时带 `fields: [{ path, message }]`，如 `displayName` 为空、`followers` 为负、`categories` 里有不存在的分类 |
| 400 | `SOURCE-INVALID` | 抓取参数不合法：未登记的来源、非 30 / 90 天窗口、请求体里带临时 URL（`sourceUrl` / `url`，`message: adhoc_url_forbidden`） |
| 404 | `NOT-FOUND` | 对象不存在或对你不可见。对不存在的博主 / 分类 / 项目 / 分派做写操作也是 404，**不写审计** |
| 409 | `JOB-STATE` | 任务 / 搁置记录当前状态不允许该操作（如取消已结束的任务） |
| 409 | `CONFLICT` | 唯一性冲突：重复分派同一博主（`already_assigned`）、`creatorKey` 已存在；筛选方案带的 `version` 不是最新（`version_conflict`，响应另带 `current` = 最新的方案） |
| 410 | `GONE` | 已下线的接口：`POST /api/ingest/jobs`（`message: use_ingest_fetch`） |
| 413 / 415 | `UPLOAD-TOO-LARGE` / `UPLOAD-TYPE` | 见「上传限制」 |
| 500 | `INTERNAL` | 服务端缺陷；参数问题不应落到这里。同时写一行 `http.unhandled` JSON 日志（方法、路径、错误名与脱敏后的信息） |
| 503 | `UNAVAILABLE` | 进程正在停机（收到 SIGTERM / SIGINT 后），`message: shutting_down`；换个副本重试即可 |

- 先鉴权后读体：未登录或无权限时，即使请求体是坏的也先得到 401 / 403。
- 写接口的请求体用 zod 校验（`apps/api/src/http/body.ts`），未知的附加字段忽略。
- 筛选方案校验失败时，除 `error.fields` 外仍保留 `errors: string[]`（`kcs.query.errors.*` 的键），供选人端直接翻译。
- 选人池游标不对：400 `VALIDATION`，`message` 为 `cursor_invalid`（被改过、签名不对、太长）或 `cursor_mismatch`（换了筛选 / 排序），`fields: [{ path: 'cursor' }]`。前端回到第 1 页即可。
- 批量分派先逐个检查再写：其中任一博主不在池内，整批都不写（400 `VALIDATION` / `not_in_pool`）。

### 分页

列表接口统一：query `page`（从 1 起，默认 1，上限 `PAGE_MAX` = 10000）、`pageSize`（默认 50，上限 100）；非数字或小于 1 按默认值，超过上限按上限截断（`page=1e20` 不会以越界整数进 SQL），不报错。响应 `{ items, total, page, pageSize }`，`total` 是分页前的匹配数；翻过最后一页得到空 `items`，`total` 照旧。常量与解析在契约 `paging.ts`（`PAGE_SIZE_DEFAULT` / `PAGE_SIZE_MAX` / `parsePaging`）。分页的接口：`GET /api/select/pool`、`POST /api/select/queries/run`、`GET /api/ops/creators`、`GET /api/ingest/jobs`、`GET /api/dev/jobs`、`GET /api/ops/batches`。所有列表的排序最后都带唯一兜底键（`id`；选人池是 `creator_id COLLATE "C"`），同值的行定序，翻页不重不漏。

**选人池的两种翻页**（`GET /api/select/pool`、`POST /api/select/queries/run`）：

- 跳页：照常用 `page`（偏移量）。
- 上一页 / 下一页：响应带 `nextCursor` / `prevCursor`（到头为 `null`），下一次请求传 `?cursor=<值>`（此时忽略 `page`，响应的 `page` 仍按页码数）。游标是键集（keyset）：记下边界行的排序值与 id，不走偏移量，深页也快（压测见下）。
- 游标由服务端 HMAC 签名，并与当时的筛选 + 排序绑定：改过或换了条件 400（见错误码）。密钥取 `KCS_CURSOR_SECRET`，缺省用 `BETTER_AUTH_SECRET`；两者都没有时进程启动随机生成一个并记 `cursor.ephemeral_secret` 警告——**多副本部署必须配置同一个 `KCS_CURSOR_SECRET`**，否则 A 副本发的游标到 B 副本是 400。
- 排序值按 float8 的 8 个字节（十六进制）携带，与 `extra_float_digits` 设置无关，`Infinity` 也能原样往返。长度上限 `CURSOR_MAX_LENGTH` = 2048。

## 认证

身份在 TinyShip（better-auth）。API 自己没有登录接口。

```
浏览器 ──POST /__login（本端 Nitro）──▶ auth.api.signInEmail ──▶ Set-Cookie better-auth.session_token
                                                              └─▶ Set-Cookie kcs_session=<token>（httpOnly，Domain=AUTH_COOKIE_DOMAIN）
浏览器 useApi ──cookie kcs_session（credentials: 'include'）──▶ API requireAuth
服务端渲染 useApi ──Authorization: Bearer <token>（从请求 cookie 取）──▶ API requireAuth
                                                └─ verifySession(token)：GET {AUTH_BASE_URL}/api/auth/get-session
                                                   → { user } → role = roleFromIdentity(user.role)
                                                     KCS 五角色原样；TinyShip `admin` → platform_admin；
                                                     其他（如管理员开通但未分工的 `user`）→ 无角色 → 处处 403 AUTH-DENIED
                                                   → 正缓存 10s（`SESSION_CACHE_MS`），未命中负缓存 5s；最多 5000 条（`SESSION_CACHE_MAX`，最久未用的先出），每分钟清一次过期；有角色才 upsert users 镜像
退出 ──POST /__logout──▶ auth.api.signOut，清两枚 cookie
```

- `AUTH_BASE_URL`：任一工作端的源站（四端共用同一 TinyShip 库，谁校验都一样）。
- 退出：TinyShip 立刻撤销；API 侧最迟 `SESSION_CACHE_MS`（默认 10s）后拒绝旧 token。
- 公开注册已关闭：`POST /api/auth/sign-up/email` 一律 400，不建账号、不发会话；社交 / 手机验证码 / 微信登录也只认已开通的账号。账号只能由管理员开通：运维端「账号」页（见下方「账号管理」），或 `pnpm db:seed:auth`。
- 没有分工的账号（开通了但没被分配 KCS 角色）：`/__login` 落 `/denied`，API 一律 403 `AUTH-DENIED`（含 `/api/auth/me`），不会被当成只读选人。
- 跳转只拼站内相对路径：`/__login` 的 `locale` 只认 `zh-CN` / `en` / `ko`，其他值（如 `/evil.example.com`）一律按 `zh-CN` 处理；宣传站交接的目标源站只取服务端运行期配置（`NUXT_PUBLIC_{SELECT,OPS,DEV}_URL`），不读请求里的地址。
- `kcs_session`：`HttpOnly`、`SameSite=Lax`，`NODE_ENV=production` 时带 `Secure`，因此生产必须走 https（浏览器对 `http://localhost` 例外）。页面脚本读不到它：浏览器端请求 API 一律 `credentials: 'include'`，由浏览器附上；服务端渲染从请求 cookie 取出后改发 `Authorization: Bearer`。API 两种都认，`Authorization` 优先（脚本 / curl 照旧用 Bearer）。
- 跨子域：设了 `AUTH_COOKIE_DOMAIN`（如 `.example.com`）时，better-auth 开 `advanced.crossSubDomainCookies`，`kcs_session`、`kcs_last_ws`、`kcs_consent` 都写在这个父域上，于是 `www.` 登录后交接到 `select.` / `ops.` / `dev.` 不用再登，`api.` 也收得到会话；工作端同时把 `NUXT_PUBLIC_COOKIE_DOMAIN` 设成同一个值。不设时全是 host-only（本机 localhost 各端口本来就共享 cookie）。better-auth 的 `trustedOrigins` = 本端 `APP_BASE_URL` / `BETTER_AUTH_URL` + 四端 `NUXT_PUBLIC_*_URL` + `AUTH_TRUSTED_ORIGINS`（逗号分隔）。
- CORS 与来源校验：API 只对 `WEB_ORIGIN`（逗号分隔的四端源站）回 `Access-Control-Allow-Origin` 并允许凭证；生产不设会记 `cors.default_origins` 警告并退回本机端口。只靠 cookie 认证的写请求（非 GET / HEAD / OPTIONS、没有 `Authorization`）还要求 `Origin` 在 `WEB_ORIGIN` 里（没有 `Origin` 时看 `Sec-Fetch-Site` 不是 `cross-site`），否则 403 `AUTH-DENIED` `origin_not_allowed`，不进业务逻辑。
- 限速：better-auth 对 `/sign-in/email` 按来源 IP 限 3 次 / 10s，超出 429 并带 `X-Retry-After`；`/__login` 表单走同一限速（被限时回 `?error=1`）。来源 IP 取 `X-Forwarded-For` 第一段；请求没带这个头（前面没有代理）时，工作端用 TCP 对端地址补上（`libs/panel/server/middleware/client-ip.ts`）——否则 better-auth 在 `NODE_ENV=production` 下拿不到 IP 会整段跳过限速。前置代理必须覆盖而不是透传客户端自带的 `X-Forwarded-For`。
- `KCS_DEV_TOKENS=1`（非生产）额外接受 `Bearer dev:<email>`，仅供本地 curl 临时用；黑盒与 E2E 都走真实邮箱登录，compose 里不再开启。

### 上传限制

- 只收 PNG / JPEG / WebP / GIF。类型按文件头魔数判定，不信客户端声明：HTML、SVG、PDF 等即使标成 `image/png` 也是 **415** `UPLOAD-TYPE`；声明了非图片类型的真图片同样 415。
- 单个文件上限 **5 MB**，超出 **413** `UPLOAD-TOO-LARGE`；超大请求体在读完之前就被拒。先校验登录与角色：未登录 401、无权限 403，不会先返回 413。
- 存储：配置了 S3（`S3_ENDPOINT` + `S3_ACCESS_KEY`，阿里云 OSS 走其 S3 兼容端点）时字节只在桶里，Postgres `assets` 只存元数据（`bytes` 为空）；未配置时字节落 Postgres。两种情况对外地址都是 `/api/assets/raw/*`。对象键带按真实类型得出的扩展名（`avatars/<uuid>.png`）。
- 桶必须**私有**（不开匿名读）。读回默认由 API 从桶取字节再吐出（`S3_READ_MODE=proxy`）；`S3_READ_MODE=redirect` 时改为 302 到 5 分钟有效的签名地址，省 API 流量，但响应头由 OSS 决定；API 走内网 endpoint 时要设 `S3_PUBLIC_ENDPOINT`（外网 endpoint，只用来签名）。对象键是随机 UUID、不会被覆盖，读回带 `Cache-Control: public, max-age=31536000, immutable`。
- 预签名不再发桶的直传地址：桶的预签名 PUT 限不了大小，所以改成本 API 的签名上传地址，同样 5 MB 上限、同样按字节判类型。
- 读回 `/api/assets/raw/*`：再按字节判定一次类型，不是四种图片之一（含修复前存进来的旧行）一律 404；响应头固定 `Content-Type: <判定出的图片类型>`、`X-Content-Type-Options: nosniff`、`Content-Disposition: inline`、`Content-Security-Policy: default-src 'none'`。
- 运营端新建博主页在上传前先按类型 / 大小拦一次，失败时给三语人话提示（`kcs.panel.uploadTooLarge` / `uploadWrongType` / `uploadFailed`）。

## 账号管理（工作端源站）

不在 API 上，而是在任一工作端源站的 Nitro 路由（`libs/panel/server/api/kcs-admin/*`），和登录同一处、直接读写 TinyShip 库。权限 `admin.users`，只有 platform_admin 有；每次请求都现查会话（`Authorization: Bearer` 或 better-auth cookie），不走缓存。错误体是 Nitro 形状：`{ statusCode, data: { error: <code> } }`。
